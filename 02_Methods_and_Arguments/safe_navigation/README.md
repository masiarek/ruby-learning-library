# `&.` skips the call when the receiver is nil

**Level:** 101 · a first-week reader who writes `x.y if x else None` in Python

**One line:** `receiver&.method(args)` returns `nil` without calling anything — not even evaluating the arguments — when the receiver is `nil`, and only `nil`; `dig` does the same across nested Hashes and Arrays, and `fetch` is the strict opposite of the lenient `[]`.

Calling a method on `nil` is the most common `NoMethodError` in Ruby, and `&.` (the "safe navigation" or "lonely" operator, in the language since Ruby 2.3 *(Not machine-checked here.)*) is the one-character answer: if the receiver is `nil`, the whole call is skipped and the expression is `nil`; if not, it is an ordinary call. Two details matter. The arguments are not evaluated when the call is skipped, so a side effect inside them does not happen. And only `nil` is skipped — `false` is an object with methods and is called normally. For nested data the same idea is `Hash#dig` and `Array#dig`, which stop at the first missing key and return `nil` instead of raising. The reverse tool is `fetch`: where `h[:missing]` quietly gives `nil`, `h.fetch(:missing)` raises `KeyError`, and `fetch` with a default or a block is the explicit way to say what a missing key means.

## Reading the output

Row 1 is the error `&.` exists for: `undefined method 'length' for nil`. Row 2 is the operator on a `nil` and on a String. Row 3 shows the argument being skipped: `nil&.concat(noisy)` prints nothing, while `"x"&.concat(noisy)` prints "(argument evaluated)" before the result. Row 4: `false&.to_s` is `"false"`, because only `nil` short-circuits. Row 5 is the everyday shape — a chain of objects where one link may be `nil` — with the unguarded version's error beside it.

Rows 6 to 8 are the Hash and Array tools. `dig` walks `:a, :b, :c` and returns `nil` at the first missing key, where `h[:a][:x][:c]` fails on `nil[]`; `[]` on a missing key is `nil`, `fetch` raises `KeyError: key not found: :zz`, and `fetch` with a default returns it. `Array#dig` works the same way, and `dig` into something that is not a container (the `1` at the end of the chain) is a `TypeError`, not a silent `nil`. Row 9 is the detail a JavaScript reader needs: `&.` guards *one* call. In `nil&.length.zero?` the `&.` returns `nil` and then `.zero?` is called on that `nil` normally — so each link that may be `nil` needs its own `&.`.

## Compared with Python

Python has no safe-navigation operator; PEP 505 proposed `?.` and `??` and was deferred *(Not machine-checked here.)*. The twin uses what is there. The conditional expression (row 2) is the direct translation and, like `&.`, it skips the arguments (row 3); `getattr(x, "y", None)` does not — it evaluates the call's arguments first, as the printed "(argument evaluated)" shows. Row 4 is the trap in the shorter `x and x.upper()` idiom: `and` drops *every* falsy value, so an empty string never gets its method called, where Ruby's `&.` and the `is not None` test skip only `None`. Rows 6 and 7 are the mirror image of Ruby's defaults: `d[k]` is strict and raises `KeyError`, `d.get(k)` is lenient and returns `None`, so a chain of `.get(k, {})` is Python's `dig`. There is no `dig` itself; row 8 writes it in five lines. Row 9 has nothing to measure: each step in a chain needs its own guard.
