# `1/3r` and `BigDecimal("0.1")` are exact where Float is not

**Level:** 201 · anyone who has been bitten by `0.1 + 0.2`

**One line:** Ruby ships two exact number types beside Float — `Rational`, with a literal suffix (`1/3r`, `0.1r`), and `BigDecimal`, a default gem with decimal digits and a rounding mode — so `0.1 + 0.2 == 0.3` is true in both; Python's `Fraction` and `Decimal` are their twins, except that Python rounds a half to even by default and refuses to mix a `Decimal` with a float where Ruby converts.

A Rational is a pair of Integers, numerator over denominator, and every operation between Rationals is exact: `1/3r + 1/6r` is `(1/2)` and `(1/3r) * 3` is `1`. The `r` suffix makes a literal — `0.1r` is exactly one tenth, where `Rational(0.1)` is the Float's exact binary value — and `Rational(1, 3)`, `Rational("1/3")` and `3.to_r` are the other spellings. A BigDecimal holds decimal digits with an arbitrary precision, so `BigDecimal("0.1") + BigDecimal("0.2")` is `BigDecimal("0.3")` — the case Float gets wrong — and it carries the rounding modes money needs (`ROUND_HALF_UP` by default, `:half_even` on request); division takes a precision, because one third has no finite decimal form. Both classes are `Numeric` and `Comparable`, both drop to a Float on `to_f` or when a Float enters the arithmetic, and `Complex` completes the tower with `2i` as a literal.

## Reading the output

Rows 1–6 are Rational. Rows 1 and 2 are the spellings; row 3 is the trap: `Rational(0.1)` does not give one tenth but the fraction the Float actually holds, because the Float was rounded before Rational ever saw it — `0.1r` and `Rational("0.1")` never go through a Float and are exact. Rows 4 and 5 are arithmetic: exact among Rationals, and a Float the moment a Float joins in (`1/3r + 0.5` is a Float). Row 6 is rounding: a Rational rounds like a Float, half away from zero, with `half: :even` on request, and `round(2)` gives a Rational back.

Rows 7–13 are BigDecimal. Row 7 is the headline, `0.1 + 0.2 == 0.3`. Rows 8 and 9 are its two `to_s` forms: the default is scientific notation — `0.3e0`, which surprises everyone once — and `to_s("F")` is positional, with an optional group size (`"3F"`) that inserts a space every three digits. Row 10 is rounding on decimal digits with a mode: `2.675` rounds to `2.68` under the default `ROUND_HALF_UP` and also under `:half_even` (7 is odd), while `2.665` goes to `2.66` under `:half_even`. Row 11 is division: `div(3, 10)` asks for ten digits, and a plain `/` stops at some precision too, so `BigDecimal("1") / 3 * 3` is not `1` — the Rational is. Rows 12 and 13 are how a BigDecimal meets a Float: `BigDecimal("0.1") == 0.1` is true and `BigDecimal("0.1") + 0.1` is `0.2e0`, and `BigDecimal("0.3") == 0.1 + 0.2` is true as well, so the Float is rounded to a short decimal — about 16 significant digits *(Not machine-checked here.)* — before it is compared or added, rather than read at its exact binary value. Rows 14–16 are Complex and the family tree: `2i` is a literal, `abs` is the modulus, `Math.sqrt(-1)` raises `Math::DomainError` rather than answer in Complex, and all three classes sit under `Numeric` and `Comparable`.

## Compared with Python

`Fraction` is `Rational` without a literal: `Fraction(1, 3)`, `Fraction("1/3")` and `Fraction("0.1")` are exact, and `Fraction(0.1)` is the same binary value as `Rational(0.1)`. The arithmetic rows agree, including the drop to `float` when one joins in; the rounding row does not, because `round(Fraction(5, 2))` is `2` — half to even, like every `round` in Python. `Decimal` is `BigDecimal` with a *context*: the precision (28 digits by default) and the rounding mode (`ROUND_HALF_EVEN`) are process-wide state, set through `getcontext()` or scoped with `localcontext()`, rather than arguments to each call — so `Decimal(1) / 3` needs no precision argument, and `quantize(Decimal("0.01"))` is the rounding call. Its default `str` is positional where BigDecimal's is scientific, and `f"{d:,}"` groups digits with commas where `to_s("3F")` uses spaces. The sharpest difference is rows 12 and 13: `Decimal("0.1") == 0.1` is `False`, because Python converts the float exactly, to `0.1000000000000000055511151231257827…`, and `Decimal("0.1") + 0.1` is a `TypeError` — Python refuses to mix the two at all, where Ruby quietly converts. `complex` and `cmath` match `Complex`, `math.sqrt(-1)` raises like `Math.sqrt(-1)`, and the `numbers` ABCs stand in for `Numeric`, with the wrinkle that `Decimal` registers as a `numbers.Number` but not as a `numbers.Real`.

## Try it

1. Add `0.1` ten times as a Float with `inject(:+)`, then with `sum`, then as `0.1r` and as `BigDecimal("0.1")`; print each total and whether it `== 1`. Then compute `19.99 * 3` in all three types. Which of the results would you put on an invoice, and which line explains why `sum` and `inject` disagree?
2. Write `to_fraction(s)` that turns a decimal string such as `"2.675"` into an exact Rational without going through a Float — split on the dot, build the numerator with `Integer()`, and use `10 ** decimals` as the denominator — then check that `to_fraction("2.675") == 2675r/1000`, that it is not `2.675.to_r`, and that `to_fraction("0.1") + to_fraction("0.2") == to_fraction("0.3")`.

```ruby
# Kata: add 0.1 ten times as a Float, a Rational and a BigDecimal, then
# multiply a price by three — and see which results equal what a calculator
# says.
require "bigdecimal"

float_sum    = Array.new(10, 0.1).inject(:+)
rational_sum = Array.new(10, 0.1r).inject(:+)
decimal_sum  = Array.new(10, BigDecimal("0.1")).inject(:+)
puts "1. ten Floats with inject(:+): #{float_sum}   == 1 is #{float_sum == 1}"
puts "2. ten Floats with sum:        #{Array.new(10, 0.1).sum}   == 1 is #{Array.new(10, 0.1).sum == 1} (sum compensates; inject does not)"
puts "3. ten Rationals:              #{rational_sum.inspect}   == 1 is #{rational_sum == 1}"
puts "4. ten BigDecimals:            #{decimal_sum.to_s('F')}   == 1 is #{decimal_sum == 1}"
puts "5. 19.99 * 3: Float #{19.99 * 3}, Rational #{(19.99r * 3).inspect}, BigDecimal #{(BigDecimal('19.99') * 3).to_s('F')}"
```
