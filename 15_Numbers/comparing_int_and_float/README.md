# `1 == 1.0` is true, but `{1 => :a}[1.0]` is `nil`

**Level:** 201 · anyone who has used a number as a Hash key

**One line:** Ruby's `==` compares an Integer with a Float by value — and exactly, so `2 ** 53 + 1 == (2 ** 53 + 1).to_f` is false — but `eql?` and `hash` keep the two classes apart, so a Hash, `uniq` and a Set see two keys where Python's dict and set see one.

Ruby has [four kinds of equality](../../01_Objects_and_Values/four_kinds_of_equality/README.md), and numbers are where the difference between two of them is easiest to see. `==` is numeric equality: it converts as needed and compares values, so `1 == 1.0`, `1 == 1r` and `1 == Complex(1, 0)` are all true. `eql?` is what a Hash uses to decide whether two keys are the same, and it insists on the same class, so `1.eql?(1.0)` is false and `1.hash` is not `1.0.hash`. Everything built on hashing — `Hash`, `Set`, `uniq`, `tally`, `group_by` — therefore keeps `1` and `1.0` apart, while everything built on `==` — `include?`, `index`, `count`, `case/when`, `<=>` — treats them as one. And when the two classes are compared, nothing is rounded first: an Integer too large for a double is compared against the Float's exact value, which is the same rule the Python library's [Comparing an `int` with a `float` ↗](https://masiarek.github.io/python-learning-library/03_Numbers/comparing_int_and_float/index.html) measures for Python.

## Reading the output

Rows 1–4 are the four questions you can ask of `1` and `1.0`. Equal in value, yes. `eql?`, no: it wants the same class. `equal?`, no: they are different objects — and `1.equal?(1)` is true because a small Integer is an immediate value, the same object everywhere. And their `hash` values differ, which is the mechanical reason for everything that follows: a Hash finds a key by its `hash` first and confirms it with `eql?`, so a key that hashes differently is a different key. Rows 5–7 are that rule at work. `{1 => :a}[1.0]` is `nil`, assigning `h[1.0]` beside `h[1]` makes a second entry, and `[1, 1.0].uniq` keeps both, as do `Set` and `tally`. Row 8 is the other family: `include?`, `index` and `count` ask `==`, so `[1].include?(1.0)` is true. Rows 9 and 10 are the two ways `case` can look at a number: `when 1` uses `===`, which for a number is `==` and matches `1.0`; `when Integer` uses `Integer === 1.0`, which is a class test and does not.

Rows 11–13 are exactness. `2 ** 53 + 1` cannot be a double — `to_f` rounds it down to `2 ** 53` — and Ruby compares the Integer with that Float's exact value rather than converting the Integer first, so `==` is false and `>` is true. The same holds at `10 ** 20 + 1` against `1e20`. Row 13 is the exception: `0.1 == 1/10r` is true even though `0.1.to_r` is not `1/10r`, because a Float and a Rational are compared by turning the Rational into a Float — so that comparison is only as exact as the Float. Row 14 is the one pair of different floats that is one key: `0.0` and `-0.0` are `==`, `eql?` and hash alike, so a Hash treats them as the same key. Row 15 closes the loop: `==` crosses every numeric class, and `eql?` crosses none.

## Compared with Python

Python draws the line in a different place. `==` between an `int` and a `float` is the same exact comparison — rows 11 and 12 print the same answers, and the Python library's twin page is about exactly that — but Python has no `eql?`, and it requires that objects which compare equal hash alike, so `hash(1) == hash(1.0)` is true and `1` and `1.0` are one dict key, one set element and one `Counter` entry. Row 6 shows the consequence that surprises people: assigning `h[1.0]` when `h[1]` exists replaces the value but keeps the key spelled `1`. Row 3 shows `is` in the role of `equal?`, with CPython's small-int cache making `one is one_again` true. Rows 9 and 10 are `match`: a literal pattern `case 1:` uses `==` and matches `1.0`, while a class pattern `case int():` is an `isinstance` test and sends `1.0` to `case float():`. Row 13 is the one place Python is the stricter of the two: `0.1 == Fraction(1, 10)` is `False`, because a `Fraction` compares with a float exactly, where Ruby converts the Rational to a Float and says true. `complex(1, 0)` behaves like `Complex(1, 0)`, and `-0.0` is one key in both languages.

So the portable rule is: between an Integer and a Float, `==` means the same thing in both languages, and the difference is entirely in what a hash-based container considers one key. Code that moves from Python to Ruby and uses mixed Integer and Float keys — a total keyed by `count / 2`, say — will find its entries split in two; `to_i` or `to_f` on the way in makes the keys one class.

def same_key?(a, b) = a.eql?(b) && a.hash == b.hash
