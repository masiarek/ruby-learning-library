# Warnings go to stderr, and `-w` finds more of them

**Level:** 201 · anyone who has seen `warning:` scroll past and wondered who wrote it

**One line:** `warn` prints to stderr; `-w` sets `$VERBOSE` to `true` and makes Ruby report unused variables, redefined methods, mismatched indentation and literal conditions; `Warning[:deprecated]` is off until `-W:deprecated` turns it on; and prepending a method to `Warning` captures every warning in-process.

Ruby has one warning channel and two switches on it. The channel is `Warning.warn`: every warning Ruby itself emits and every `warn "…"` in your code goes through that one method, and it writes to stderr, so a program's stdout stays clean for the next program in the pipe. The first switch is `$VERBOSE`: `false` by default (warnings on, lint off), `true` under `-w` (lint on: parse-time checks for unused variables, mismatched indentation and literals in conditions, plus a run-time check for redefined methods), `nil` under `-W0` (everything off, `warn` included). The second is per category: `Warning[:deprecated]` is `false` by default, so deprecation warnings — including `warn …, category: :deprecated` in your own code and the "literal string will be frozen" warning that [chilled literals ↗](https://masiarek.github.io/ruby-text-learning-library/05_Literals/literals_are_chilled/index.html) emit — are silent until `-W:deprecated` or `Warning[:deprecated] = true`; `:experimental` is on by default, `:performance` off. Because the channel is one method on a module, a test can capture warnings by prepending a module to `Warning`'s singleton class. The program shows all of this through child processes, since a warning is stderr and stderr is not what a page's output block records.

## Reading the output

Row 1 is the channel: `puts` lands in the child's stdout, `warn` in its stderr. Row 2 adds `uplevel: 0`, and the warning gains the `-e:1: warning:` prefix that Ruby's own warnings carry. Row 3 is the category switch: by default `warn "old", category: :deprecated` prints nothing and `Warning[:deprecated]` is `false`; under `-W:deprecated` both change. Row 4 is `$VERBOSE` under the three settings, and shows that `-W0` silences even a plain `warn`. Row 5 lists the four categories Ruby 4.0 knows and their defaults: only `:experimental` is on.

Row 6 runs one sloppy file three ways. Plain `ruby` runs it silently. `ruby -w` reports six lines: the parse-time warnings first (an unused variable on line 2, a literal in a condition on line 10, the `end` on line 16 that does not line up with its `def` on line 14, another unused variable on line 15), then, once execution reaches the second `def greet`, the run-time pair "method redefined; discarding old greet" and "previous definition of greet was here". `ruby -c` parses without running and prints `Syntax OK` — a syntax check, not a lint; none of the six warnings are errors. Row 7 captures in-process: after the prepend, `warn "captured one"` reaches our method with `category` `nil`; `warn "captured two", category: :deprecated` never reaches it, because a disabled category is filtered before `Warning.warn` is called; after `Warning[:deprecated] = true`, the third one arrives with its category. Row 8 is the chilled-literal warning: `s << "x"` on a literal succeeds silently by default and prints "literal string will be frozen in the future" under `-W:deprecated`.

## Compared with Python

Python's `warnings.warn` also writes to stderr (row 1), but it always prefixes `file:line: Category:` — and `stacklevel=2` moves the blame from the `warn` call to its caller, which is what `uplevel:` does in Ruby (row 2). The switches are per category and per module rather than a global `$VERBOSE`. Row 3 is the one that surprises: a `DeprecationWarning` is shown when it is raised in `__main__` and hidden when the same call sits in an imported module — the default filter is meant to nag the developer of the code, not its user — and `-W default` or `-X dev` shows it everywhere. Row 4: `-W error` turns the warning into an exception (the child exits 1 with `UserWarning: careful` as the last line of a traceback), `-W ignore` drops it. Row 5 asks a child for each category and reads off the defaults: `PendingDeprecationWarning`, `ImportWarning` and `ResourceWarning` are hidden even from `__main__`. Row 6: there is no `-w` lint pass; the closest thing is the compiler's `SyntaxWarning` for constructs it can tell are wrong, such as `is` with a literal or an `assert` on a tuple. Row 7 is the in-process capture, built in as `warnings.catch_warnings(record=True)` — note the `simplefilter("always")` so the `DeprecationWarning` is recorded too. Row 8 is the structural difference under all of it: `Warning` is a subclass of `Exception`, which is why a warning can become an error at all, where Ruby's `Warning` is a module with a method. Dev mode also turns on `ResourceWarning` and extra runtime checks; the twin prints only `sys.flags.dev_mode` and `sys.warnoptions`. *(Not machine-checked here.)*

```ruby
# Exercise 1: write a sloppy file, run it under ruby -w and without, and print what
# each run said on stderr with the temp-dir path cut to the base name.

require "open3"
require "rbconfig"
require "tmpdir"

SLOPPY = <<~RUBY
  def total(items)
    count = items.size
    items.sum
  end

  def total(items)
    items.sum
  end

  puts total([1, 2, 3])
RUBY

Dir.mktmpdir do |dir|
  path = File.join(dir, "sloppy.rb")
  File.write(path, SLOPPY)
  [["without -w"], ["with -w", "-w"]].each do |label, *flags|
    out, err, status = Open3.capture3(RbConfig.ruby, *flags, path)
    puts "#{label}: stdout #{out.chomp.inspect}, status #{status.exitstatus}"
    if err.empty?
      puts "   stderr: (empty)"
    else
      err.each_line { |line| puts "   stderr: #{line.chomp.sub(%r{\A\S*/}, '')}" }
    end
  end
end
```
