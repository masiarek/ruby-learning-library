# `exit` raises `SystemExit`

**Level:** 201 · anyone writing a command-line tool, or a `rescue` around code that might call `exit`

**One line:** `exit` is not a system call but a `raise` of `SystemExit`, so `ensure` clauses and `at_exit` handlers run, a `rescue SystemExit` can stop it, and a bare `rescue` cannot see it — while `exit!` really does leave at once, `abort` is `exit 1` with a message on stderr, and an unrescued `Interrupt` ends the process by the signal, not by a status.

Ending a Ruby process is an exception in flight. `exit` (and `exit 3`, `exit true`, `exit false`) raises `SystemExit`, whose `status` becomes the process's exit status once it reaches the top; on the way up it unwinds like any exception — `ensure` clauses run, a `rescue SystemExit` (or `rescue Exception`) can catch it and carry on, and because `SystemExit` is not a `StandardError` a bare `rescue` lets it through. After the top is reached, the `at_exit` handlers run, last-registered first, and only then does the process end. `exit!` skips all of that — no unwinding, no handlers — and `abort("msg")` prints the message to stderr and then does an ordinary `exit 1`. An exception that nobody rescues is reported on stderr, the process exits with status 1, and the `at_exit` handlers still run, with `$!` holding the exception. `Interrupt`, what Ctrl-C raises, is a `SignalException`, not a `StandardError`; left unrescued, Ruby re-delivers the signal so that the parent sees a process killed by SIGINT rather than a status. The program below cannot show any of this in its own process without ending it, so each row starts a child Ruby with `RbConfig.ruby -e` and prints the child's stdout, stderr and exit status.

## Reading the output

Row 1: `exit` inside `begin … rescue SystemExit => e` is caught, its `status` is 0 and `success?` is true, and the child prints `still running` and ends with status 0 — the exit was cancelled. Row 2 is the same with a bare `rescue`: nothing is printed, not `caught` and not `after`, and the status is 3; `SystemExit` passed straight through. Row 3 maps the argument to the status: `3` is 3, `true` is 0, `false` is 1.

Row 4 registers three `at_exit` blocks and prints `main done` first, then `third`, `second`, `first` — reverse order, like a stack of cleanups. Row 5's `exit! 4` prints nothing: the handler never ran, and the status is still 4. Row 6 is `abort`: the message on stderr, the handler on stdout, status 1. Row 7 is an uncaught `RuntimeError`: `before` on stdout, the one-line report `-e:1:in '<main>': boom (RuntimeError)` on stderr, status 1 — and the `at_exit` handler still ran, and found the exception in `$!` (the child's stdout and stderr are captured as two streams, so the output cannot show which of the two lines came first).

Row 8 is the signal. `raise Interrupt` is rescued as a `SignalException` with `signo` 2. A real SIGINT, sent by the child to itself and not rescued, leaves no exit status at all: the parent sees `killed by signal 2` (the frame label in the stderr line is masked, since which frame the signal lands in is the interpreter's business), which is how a shell tells a Ctrl-C from an `exit 130`. Rescued as `Interrupt`, the same signal is an ordinary exception and the child exits 0. Row 9 is this program's own `at_exit` handler, registered on its first lines and printed after everything else.

## Compared with Python

Python ends a process the same way — `sys.exit` raises `SystemExit`, `finally` clauses run, `except SystemExit` cancels it (row 1), and `except Exception` does not see it (row 2) because `SystemExit` hangs off `BaseException`. Row 3 has a trap in the same words: `sys.exit(True)` exits with status *1*, because `True` is the integer 1, where Ruby's `exit true` is success — and `sys.exit(False)` is 0. `atexit.register` (row 4) runs its handlers in reverse like `at_exit`, and `os._exit` (row 5) is `exit!`. Row 6: there is no `abort`; `sys.exit("fatal: giving up")` prints the string to stderr and exits 1, which is the same thing. Row 7 differs in what the handler can see: the traceback has already been printed when `atexit` runs, and `sys.exception()` is `None` — Ruby's `$!` is still set. Row 8: `KeyboardInterrupt` is what the default SIGINT handler raises, a `BaseException`; uncaught, it too ends the process by the signal (`subprocess` reports a negative return code, printed here as `killed by signal 2`). The twin prints only the last line of each child's stderr, because CPython's traceback layout — the source echo and the caret lines — differs between 3.12 and 3.14, while the last line does not.
