# A bare `rescue` catches `StandardError`, not everything

**Level:** 201 · anyone who has written `rescue => e` and wondered what it misses

**One line:** `rescue` with no class list means `rescue StandardError`, and `SystemExit`, `Interrupt`, `NoMemoryError`, `SystemStackError` and every `ScriptError` — `LoadError`, `SyntaxError` and, surprisingly, `NotImplementedError` — sit outside that branch, which is why `exit` still exits through a bare `rescue` and why `rescue Exception` is the anti-pattern.

Every Ruby exception descends from `Exception`, but the tree has two halves. `StandardError` heads the half a program is expected to handle: `RuntimeError`, `ArgumentError`, `TypeError`, `NameError`, `KeyError`, `IOError`, the `Errno` family and their subclasses. The other half is for things the interpreter is telling you about — the process is exiting (`SystemExit`), a signal arrived (`Interrupt`), memory or stack ran out (`NoMemoryError`, `SystemStackError`), or the code itself could not be loaded or is unfinished (`ScriptError`, with `LoadError`, `SyntaxError` and `NotImplementedError` under it). A `rescue` clause with no class list catches `StandardError` and nothing above it, so the second half passes straight through — which is what you want: `exit` inside a rescued block still exits, Ctrl-C still stops the program, and a method left as `raise NotImplementedError` is not quietly turned into a return value. `rescue Exception` catches both halves, and the program shows what that does to `exit`.

## Reading the output

Row 1 prints each class's ancestors, classes only (the mix-ins `DidYouMean::Correctable` and `ErrorHighlight::CoreExt` are filtered out), stopping before `Object`. Read the right-hand end of each line: the first twelve chains pass through `StandardError`, the other seven do not. A few placements are worth remembering — `KeyError` and `StopIteration` are `IndexError`s, `FrozenError` is a `RuntimeError`, `Errno::ENOENT` is a `SystemCallError` — and two are traps: `SystemStackError` hangs directly off `Exception`, and `NotImplementedError` is a `ScriptError`, beside `LoadError` and `SyntaxError`, not a `StandardError`.

Row 2 raises ten of those classes inside a bare `rescue` that sits inside a `rescue Exception`. The first four are caught where you would expect; the other six say `SLIPPED PAST it` — the bare `rescue` never ran, and only the outer `rescue Exception` stopped them. Row 3 states the rule the row demonstrates: a bare `rescue` is `rescue StandardError`, `Exception` itself is not a `StandardError`, and `StandardError`'s superclass is `Exception`.

Row 4 is the anti-pattern in one line: `exit 1` raises `SystemExit`, `rescue Exception` catches it, and the program carries on with the message printed — the process that was told to stop did not. The same clause would swallow a Ctrl-C (`Interrupt`) and a stack overflow. Rows 5 and 6 are the two cases that bite in real code: a method that calls itself without end raises `SystemStackError` ("stack level too deep"), and an abstract method left as `raise NotImplementedError` raises a `ScriptError` — both pass through `rescue => e` untouched, and the output shows only the outer, specific `rescue` seeing them. If you want to catch a `NotImplementedError`, name it.

## Compared with Python

Python's tree has the same two halves but draws the line elsewhere and — the important part — its *bare* form catches the wrong half. `BaseException` is the root; `Exception` is the branch a program handles; only `SystemExit`, `KeyboardInterrupt` and `GeneratorExit` (plus `BaseExceptionGroup`) sit outside it. Row 1 shows the placements: `KeyError` and `IndexError` are `LookupError`s, `ZeroDivisionError` is an `ArithmeticError`, `FileNotFoundError` is an `OSError`, and `RecursionError`, `NotImplementedError` and `MemoryError` are all ordinary `Exception`s — the three Ruby keeps outside `StandardError`. Row 2 confirms it: `except Exception` catches `MemoryError`, `NotImplementedError` and `RecursionError`, and only `SystemExit` and `KeyboardInterrupt` slip past. Row 3 is the reversal: a bare `except:` is `except BaseException:`, so it *does* catch `SystemExit` — Ruby's bare `rescue` is the safe default, Python's bare `except:` is the anti-pattern, and `except Exception:` is the Python spelling of Ruby's `rescue => e`. Row 4 shows the consequence — `sys.exit(1)` swallowed by a bare `except:`. Rows 5 and 6 print the opposite of the Ruby rows: a real stack overflow (`RecursionError`, a `RuntimeError`) and a `NotImplementedError` (also a `RuntimeError`) are both caught by `except Exception`.

`KeyboardInterrupt` is what Python's default SIGINT handler raises, and the Python library's [Ctrl-C is a signal ↗](https://masiarek.github.io/python-learning-library/02_Projects_and_Environments/ctrl_c_is_a_signal/index.html) shows how `signal.signal()` replaces that handler; Ruby's `Interrupt` is the same idea, and the [exit lesson](../exit_at_exit_and_system_exit/README.md) here measures it in a child process.

## Try it

1. Write `safe_call`, a method that yields to its block and returns `[:ok, value]`, or `[:error, e.class]` when the block raises a `StandardError`. Show it on a good block, on `Integer("abc")` and on `{}.fetch(:missing)`; then show that `safe_call { exit 2 }` lets the `SystemExit` through — catch it at the top level with `rescue SystemExit => e` and print `e.status`.
2. Write `retry_on(*classes, times:)` that yields and retries only when the block raises one of the listed classes, re-raising anything else at once. Test it with a block that raises `ArgumentError` twice and then succeeds, and with a block that raises `NotImplementedError`.

```ruby
# Exercise 1: safe_call runs a block and turns a StandardError into a value, while
# letting exit (SystemExit) pass straight through to the top level.

def safe_call
  [:ok, yield]
rescue StandardError => e
  [:error, e.class]
end

puts "1. a value comes back tagged :ok"
p safe_call { 21 * 2 }

puts "2. a StandardError comes back tagged :error"
p safe_call { Integer("abc") }
p safe_call { {}.fetch(:missing) }

puts "3. exit is not a StandardError, so it passes through safe_call"
begin
  safe_call { exit 2 }
  puts "   never printed"
rescue SystemExit => e
  puts "   SystemExit reached the top level with status #{e.status}"
end
```
