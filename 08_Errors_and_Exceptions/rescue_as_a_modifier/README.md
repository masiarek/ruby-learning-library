# `rescue` works as a modifier, for `StandardError` only

**Level:** 201 · anyone tempted to write `value = risky rescue default`

**One line:** `expr rescue fallback` evaluates `expr` and, if it raises a `StandardError`, yields `fallback` instead; it binds looser than assignment, cannot stand bare in an argument list, and hides every `StandardError` alike — a typo's `NoMethodError` as readily as the `ArgumentError` you meant.

`rescue` has a one-line form, in the family of `if` and `unless` modifiers: `expr rescue fallback`. It catches `StandardError` — the same default as a bare `rescue` clause — and nothing else, so a `NotImplementedError` or a `SystemExit` passes through it. It binds after assignment: `x = expr rescue 0` is `x = (expr rescue 0)`, which is the reading you want, and in an argument list it needs its own parentheses because a bare `p(expr rescue 0)` does not parse. Two related rules concern blocks: since Ruby 2.5 a `do … end` block may carry `rescue`, `else` and `ensure` clauses like a method body, but a `{ }` block may not — the modifier is the only `rescue` a brace block can hold. The form is popular for parsing — `Integer(text) rescue 0` — and the same program shows the alternative that does not swallow unrelated errors: `Integer(text, exception: false)` returns `nil` for bad input and still raises for everything else.

## Reading the output

Row 1 is the form in use: `Integer("abc")` raises `ArgumentError`, so the expression yields `0`; `Integer("42")` does not raise, so the fallback is never evaluated and `x` is `42`. Row 2 raises a `NotImplementedError` under the modifier and it comes straight through to the outer `rescue NotImplementedError` — the modifier is `rescue StandardError`, nothing wider. Row 3 is precedence: `value = raise("boom") rescue "fallback"` leaves `value` holding `"fallback"`, because the modifier binds before the assignment does; and the `compiles?` helper (which asks `RubyVM::InstructionSequence.compile` and reports the class of the failure) shows that `p(expr rescue 0)` is a `SyntaxError` while `p((expr rescue 0))` is fine.

Row 4 is the method-level clause from the [first lesson](../rescue_ensure_else_and_retry/README.md), for contrast with the one-liner. Row 5 compiles two blocks that differ only in their delimiters: the `do … end` block with a `rescue => e` clause compiles and, when run, rescues; the `{ }` block with the same clause is a `SyntaxError`. Row 6 shows the way round it — inside braces, the modifier form is legal. Row 7 is why the modifier is so often wrapped around `Integer()`: `to_i` never raises (it reads `"12abc"` as `12` and `"abc"` as `0`), `Integer()` refuses anything that is not a whole number literal, and `Integer(text, exception: false)` gives `nil` without a rescue at all.

Row 8 is the argument against the modifier. `nil.upcse` is a typo for `upcase`; it raises `NoMethodError`, a `StandardError`, and the modifier turns it into `"default"`. The bug is now invisible. The rule of thumb: use the modifier only when the expression can raise exactly one kind of error you have already thought about, and prefer `exception: false`, `fetch` with a default, or `dig` where they exist.

## Compared with Python

Python has no expression form of `try` at all — row 1 compiles `x = int('abc') except ValueError: 0` and gets a `SyntaxError`; that syntax was proposed in PEP 463 and rejected. *(Not machine-checked here.)* The idioms in its place are a small helper (`or_default(f, default)`, which takes a `lambda`), and `contextlib.suppress`, which is a `with` block rather than an expression: row 2 shows it catching only the class it is given, and row 3 the consequence of it being a statement — when the suppressed line raises, the rest of the block is skipped, assignment included, so the default has to be set *before* the block. Row 4 matches Ruby's row 4 only in spirit: there is no function-level `except`, so the `try` is written out. Row 5 is Python's version of the brace-block rule: `try` cannot appear inside a `lambda` or any other expression, with or without parentheses. Row 6 lists what Python reaches for instead of a catch-all: `dict.get`, `getattr` with a default, `next(it, default)`. Row 7 is the parsing difference: `int()` has no `to_i` beside it — `"abc"` and `"12abc"` both raise `ValueError`, and only surrounding whitespace is forgiven. Row 8 is the same trap in the same shape: a catch-all helper turns the typo's `AttributeError` into `'default'`.
