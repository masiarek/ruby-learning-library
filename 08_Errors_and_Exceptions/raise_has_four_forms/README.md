# `raise` has four forms

**Level:** 201 · anyone who has only ever written `raise "something went wrong"`

**One line:** `raise "msg"` is a `RuntimeError`, `raise Klass` an instance whose message is the class name, `raise Klass, "msg"` and `raise Klass.new("msg")` the two explicit forms — and a bare `raise` inside a `rescue` re-raises the current exception, `$!`, while anything that is not an exception is a `TypeError`.

`raise` is not syntax; it is a method on `Kernel`, and its argument list is a small protocol. With a string it builds a `RuntimeError`. With a class it calls that class's `exception` method with no arguments, which by default is `new`, so the message is the class name. With a class and a string it calls `Klass.exception("msg")`. With an instance it raises that instance, and an instance plus a string raises a copy carrying the new message. A third argument replaces the backtrace — an `Array` of strings, most usefully `caller`, so an error is blamed on the line that called a validation method rather than the line inside it. With no argument inside a `rescue` clause it re-raises `$!`, the exception being handled; with no argument anywhere else there is nothing to re-raise and Ruby raises a `RuntimeError` with an empty message. `fail` is the same method under a second name. Two globals track the current exception: `$!` is the object and `$@` is its backtrace, both set while a `rescue` clause runs and cleared after it.

## Reading the output

Rows 1 to 4 are the four forms. In row 2 the message is `"ArgumentError"` — the class name — because `ArgumentError.exception` with no argument is `ArgumentError.new` with no argument, and `Exception#message` defaults to the class name. Row 4's second line shows the instance-plus-string form: the `ArgumentError` built with `"original"` reaches the handler saying `"replaced"`, because `raise obj, msg` calls `obj.exception(msg)`, which returns a copy with the new message.

Row 5 is the bare `raise` inside a `rescue`: the outer handler receives the very same object (`equal?` is true), not a copy or a wrapper, so the inner clause can log and step aside. Row 6 is the bare `raise` with nothing to re-raise: a `RuntimeError` whose message is the empty string. Row 7 shows the third argument — the two-element array becomes the backtrace verbatim, and with `caller` the first backtrace entry names `Object#validate`, the method that called `check`, rather than `check` itself, which is the point of passing it.

Row 8: `fail` is `raise` — same class, same message. Row 9 is what happens when the argument is not an exception: an `Integer`, a class that does not descend from `Exception`, and a string followed by a second string (there is no `String.exception`) all raise `TypeError` with the message `exception class/object expected`. Row 10 prints the two globals: inside the `rescue`, `$!` is the rescued object and `$@` is its backtrace array; after the clause, `$!` is `nil` again. Row 11 makes the protocol visible: a class that overrides `self.exception` sees `raise Custom` arrive with no arguments and `raise Custom, "msg"` arrive with `["msg"]` — this is the hook `raise` calls, and the [custom exception lesson](../custom_exception_classes/README.md) uses its instance-side twin.

## Compared with Python

Python has one form — `raise <instance>` — and the shorthand `raise Klass`, which calls the constructor with no arguments (row 2: `args=()`, an empty tuple, not the class name). A string is not an exception, so row 1 is a `TypeError` in Python where it was the most common form in Ruby. The two-argument `raise Klass, "msg"` is Python 2 syntax and a `SyntaxError` in Python 3 (row 3, via `compile`), and there is no "instance plus new message" form (row 4). Row 5 matches exactly — a bare `raise` inside `except` re-raises the same object — and row 6 is a `RuntimeError` in both languages (the twin prints the type only; CPython's message, `No active exception to reraise`, is not keyed). Row 7 is the structural difference: a Python traceback is a chain of frame objects, not strings, so the replacement is `exc.with_traceback(tb)`, and the twin shows the borrowed frames counted before and after. Row 8 has no `fail`. Row 9 agrees on the `TypeError`. Row 10 replaces `$!` and `$@` with `sys.exception()` (3.11+) and `sys.exc_info()`, which likewise revert to `None` after the `except` block. Row 11 shows `raise Klass` is a plain constructor call — there is no `exception` hook to override.

```ruby
# Exercise 1: raise with the two-argument form, rescue and report it, re-raise with a
# bare raise, and show that the outer handler receives the very same object.

def must_be_positive(n)
  raise ArgumentError, "expected a positive number, got #{n.inspect}" unless n.is_a?(Numeric) && n.positive?
  n
end

puts "1. a good value passes through"
puts "   must_be_positive(5) -> #{must_be_positive(5)}"

puts "2. a bad value is reported inside, then re-raised to an outer handler"
begin
  begin
    must_be_positive(-2)
  rescue ArgumentError => inner
    puts "   inner handler: #{inner.class}: #{inner.message}"
    raise
  end
rescue ArgumentError => outer
  puts "   outer handler got the same object: #{outer.equal?(inner)}"
end

puts "3. a non-number is reported with inspect, so a string shows its quotes"
begin
  must_be_positive("7")
rescue ArgumentError => e
  puts "   #{e.message}"
end
```
