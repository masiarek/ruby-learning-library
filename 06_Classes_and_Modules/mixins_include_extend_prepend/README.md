# Mixins: `include`, `extend`, `prepend`

**Level:** 201 · a reader who knows Python's multiple inheritance and wants to see what Ruby does instead

**One line:** `include` inserts a module into the class's ancestor chain *behind* the class, `prepend` inserts it *in front* so the module's method runs first and `super` reaches the class, and `extend` does an `include` into one object's singleton class.

Ruby has single inheritance and modules. A module holds methods but cannot be instantiated or subclassed; a class *mixes it in*, and the effect is nothing more than a new entry in `ancestors`, the list a method call walks from left to right. `include Greeting` puts `Greeting` just after the class, so the class's own methods win and `super` inside them reaches the module. `prepend Loud` puts `Loud` *before* the class, so `Loud#greet` runs first and its `super` reaches the class's `greet` — the way to wrap a method without touching it. `extend Shouting` on one object mixes the module into that object's singleton class, so only that object gains the methods; `extend` inside a class body does the same to the class object, which is how a module supplies class methods. `Comparable` and `Enumerable` are the standard library's two famous mixins: each asks for one method (`<=>` or `each`) and gives back a family. The program builds the chain step by step and records the order in which the methods actually run.

## Reading the output

Row 1 is `include`: `Person.ancestors` reads `[Person, Greeting, Object]`, and `ann.greet` finds `greet` in the second entry. Row 2 shows the two questions you can ask a class about its mixins. Row 3 is `extend` on one object: `bob.shout` works and `ann.shout`, on another instance of the same class, does not — the module went into `bob`'s singleton class alone. Row 4 is `extend` in a class body: `Registry.count` is now a class method, and `Registry.singleton_class.include?(Counting)` shows where it went.

Rows 5 and 6 are `prepend`. The chain now begins `[Loud, Person, Greeting, Object]`, and when `ann.greet` is called the trace records `Loud` first, then `Person`, then `Greeting`: each level called `super`, each `super` went one step to the right, and the final string was built from the inside out and upcased on the way back. Row 7 shows that a module already in the chain is not added twice — `include` is idempotent.

Rows 8 and 9 are the standard mixins. `Version` defines only `<=>`, and `Comparable` supplies `<`, `clamp` and the rest; `Deck` defines only `each`, and `Enumerable` supplies `sort`, `include?` and the rest of its toolbox ([Enumerable is a mixin](../../05_Enumerable_and_Iteration/enumerable_is_a_mixin/README.md) shows what `each` buys). Row 10 is the boundary: a module is not a class, so `Class.new(Greeting)` — trying to use it as a superclass — is a `TypeError`.

## Compared with Python

A Python mixin is an ordinary class listed among the bases, and the ancestor chain is `__mro__`, computed by the C3 algorithm from the order of those bases. Rows 1 and 2 are therefore the same picture with different names: `['Person', 'Greeting', 'object']`, `issubclass`. Row 3 has no direct counterpart — Python cannot mix a class into one instance — and the closest thing is binding a single function onto the object with `types.MethodType`, which the twin does. Row 4 gets class methods from a base class that defines `@classmethod`s, where Ruby uses `extend`. The real difference is rows 5 and 6: there is no `prepend`. With `class Person(Loud, Greeting)` the MRO reads `['Person', 'Loud', 'Greeting', 'object']` — the class itself always comes first — so `Person.greet` runs *before* `Loud.greet`, and the trace and the result string come out in the opposite order to Ruby's. To wrap a method from outside in Python you subclass, or you decorate it. Row 7 is a contrast too: listing a base twice is a `TypeError`, where Ruby's second `include` is a no-op. Rows 8 and 9 show Python's counterparts to the standard mixins — `functools.total_ordering` (two methods in, six out; no `clamp`, so the twin nests `min` and `max`) and `collections.abc.Sequence` (`__getitem__` and `__len__` in; `__contains__`, `__iter__`, `index` and `count` out). Row 10 closes the loop: a Python mixin is a class, so `Greeting()` is a perfectly good instance and `Greeting` a perfectly good base.

```ruby
# Exercise 1: a Timestamped module whose `save` runs first when prepended and
# is shadowed by the class's own `save` when merely included.

module Timestamped
  def save
    "timestamped(" + super + ")"
  end
end

class PrependedRecord
  prepend Timestamped

  def save = "PrependedRecord#save"
end

class IncludedRecord
  include Timestamped

  def save = "IncludedRecord#save"
end

puts "PrependedRecord.ancestors.first(2): #{PrependedRecord.ancestors.first(2).inspect}"
puts "PrependedRecord.new.save:           #{PrependedRecord.new.save}"
puts "IncludedRecord.ancestors.first(2):  #{IncludedRecord.ancestors.first(2).inspect}"
puts "IncludedRecord.new.save:            #{IncludedRecord.new.save}"
puts "included: Timestamped#save is reached only through super, which IncludedRecord#save never calls"
```
