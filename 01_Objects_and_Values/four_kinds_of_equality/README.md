# Ruby has four kinds of equality

**Level:** 201 · anyone who has typed `==` in Ruby and wondered what `eql?` and `===` are for

**One line:** `equal?` is identity, `==` is value, `eql?` is value without type conversion (the test `Hash` keys use), and `===` is "does this pattern match that value?" (the test `case`/`when` runs); Python has `is`, `==` and `isinstance`, and its `==` does the job of `eql?` too, so `1 == 1.0`, `hash(1) == hash(1.0)` and `{1: "a"}[1.0]` all say yes.

Ruby gives every object four methods for four different questions. `a.equal?(b)` asks whether they are the same object; you never override it. `a == b` asks whether they have the same value; you override it in your own classes. `a.eql?(b)` asks for the same value *and* the same type, and `Hash` and `uniq` use it together with `hash` — which is why `1` and `1.0` are two different hash keys in Ruby. `a === b` asks whether `a`, read as a pattern, matches `b`: a class matches its instances, a regexp its matches, a range its members, a proc whatever it returns truthy for — and `case`/`when` calls it on every `when`. Python has three of the four and folds the third into the second. The program prints six numbered groups, and the Python twin prints the same rows.

## Reading the output

- **Row 1.** `equal?` is identity. Two `[1]` literals are two objects; a variable is `equal?` to itself; `1` and `:s` are `equal?` to themselves because there is only one of each, while two `"xy"` literals are two strings.
- **Row 2.** `==` is value. The two arrays are `==`, and so are `1` and `1.0` — `Integer#==` converts across numeric types. `"a" == :a` is `false` (a symbol is not a string) and `nil == false` is `false`.
- **Row 3.** `eql?` is `==` without the conversion: `1.eql?(1.0)` is `false`, their `hash` values differ, so `{1 => :int}[1.0]` is `nil` and `[1, 1.0].uniq` keeps both. Define `eql?` and `hash` together when your objects become hash keys — [that page](../../07_The_Object_Model/eql_and_hash_for_hash_keys/README.md) shows what happens if you define only `==`.
- **Row 4.** `===` reads its left side as a pattern. A class matches only its instances, so `Integer === 1.0` is `false`; a regexp matches the strings it matches; a range matches the values it covers; a lambda matches what it returns truthy for; and a plain value such as `"cat"` matches what it is `==` to.
- **Row 5.** `case x when p` evaluates `p === x`, which is how one `case` can dispatch on a class, a regexp, a range and a lambda without spelling any of those tests out.
- **Row 6.** A class you write starts with identity for all four. After `def ==`, `==` and `===` agree (the default `===` calls `==`), but `eql?` still says `false`, so two equal points are still two hash keys.

## Compared with Python

Python has `is` for identity and `==` for value, and the two rows agree with Ruby's — with one implementation detail worth knowing: CPython caches small integers and interns identifier-like string literals, so `x = 1; y = 1; x is y` and `s = "s"; t = "s"; s is t` are `True` where Ruby says two literals are two strings, and a string built at run time with `join` is a separate object (row 1). There is no `eql?` because `==` and `hash()` already agree across numeric types: `hash(1) == hash(1.0)` is `True`, `{1: "int"}[1.0]` finds the entry, `{1: "int"}[True]` finds it too since `bool` is an `int`, and the set `{1, 1.0}` has one element (row 3) — the [Python library's page on comparing `int` and `float` ↗](https://masiarek.github.io/python-learning-library/03_Numbers/comparing_int_and_float/index.html) measures that side in depth. There is no `===`; each of Ruby's patterns has its own spelling — `isinstance`, `re.search`, `in`, a call (row 4) — and `match`/`case` reproduces `case`/`when` with class patterns for the `isinstance` cases and guards for the rest (row 5). A class starts with identity `==` here too; defining `__eq__` makes the objects unhashable (`__hash__` becomes `None`) until you define `__hash__` as well, where Ruby quietly keeps identity hashing and gives you two keys (row 6).

## Try it

1. Print one table with four columns — `equal?`, `==`, `eql?`, `===` — for the pairs `[1, 1]`, `[1, 1.0]`, `["a", "a"]`, `[:a, :a]`, `[[1], [1]]`, `[Integer, 1]`, `[1..3, 2]` and `[/a/, "cat"]`. Which column is the only one that is ever `true` when `==` is `false`?
2. Write a `Money` class with `amount` and `currency`. Define `==` so that two equal amounts in the same currency compare equal, then show that a hash still treats them as two keys; define `eql?` and `hash` and show the hash now sees one key. What does `Money.new(1, "USD") == 1` return, and why must `==` check the class of its argument first?

```ruby
# Kata: one table, four columns -- equal?, ==, eql? and === -- for eight pairs.
# Read it row by row: only equal? cares about identity, only eql? cares about
# the type, and only === treats the left side as a pattern.

pairs = [
  [1, 1], [1, 1.0], ["a", "a"], [:a, :a], [[1], [1]],
  [Integer, 1], [1..3, 2], [/a/, "cat"]
]

puts "   a         b         equal?   ==       eql?     ==="
pairs.each do |a, b|
  cells = [a.equal?(b), a == b, a.eql?(b), a === b].map { |v| v.to_s.ljust(8) }
  puts "   #{a.inspect.ljust(9)} #{b.inspect.ljust(9)} #{cells.join(' ')}".rstrip
end
```
