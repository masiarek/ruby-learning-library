# `freeze` is shallow and raises `FrozenError`

**Level:** 201 · anyone who has seen `# frozen_string_literal: true` at the top of a file and wondered how far it reaches

**One line:** `freeze` makes one object immutable — every later mutation raises `FrozenError`, naming the object — but only that object: what it contains stays mutable unless you freeze it too (`Ractor.make_shareable` does that for you), integers, symbols and `nil` are born frozen, and the magic comment freezes every string literal in its file; Python has no `freeze` and gets immutability from the type — `tuple`, `frozenset`, `str`, `MappingProxyType`, `dataclass(frozen=True)` — with the same shallowness and one back door.

Any Ruby object can be frozen, and `frozen?` reports it. A frozen object rejects every change: `<<` on a string, `[]=` on a hash, a setter or `instance_variable_set` on an instance of your own class — all raise `FrozenError`, and the message says which object refused. Freezing is a property of the object, not of the variable, so a frozen array can still hold unfrozen strings that anyone may change; that is what "shallow" means, and `Ractor.make_shareable` exists to freeze a whole structure in one call because a Ractor may only share objects that cannot change. Some objects are frozen from birth — every `Integer`, `Symbol`, `nil`, `true`, `false`, `Float` and `Range` — and a string literal is the deliberate exception: in Ruby 4.0 it is *chilled*, mutable but flagged, unless the file opens with `# frozen_string_literal: true`. The program prints seven numbered groups; group 6 starts two child Rubies, one on a file with the comment and one without.

## Reading the output

- **Row 1.** `freeze` returns its receiver, so `s.freeze.frozen?` reads naturally. `dup` gives an unfrozen copy; `clone` copies the frozen state along with the object.
- **Row 2.** The message is the same shape for every class — `can't modify frozen String: "abc"` — and names the object by its `inspect`. `FrozenError` is a `RuntimeError` and so a `StandardError`, which is why a bare `rescue` catches it.
- **Row 3.** `[[1]].freeze` freezes the outer array only. The inner array still accepts `<<`, and only the outer one raises.
- **Row 4.** `Ractor.shareable?` is `false` for the frozen outer array while its contents are mutable; `Ractor.make_shareable` freezes the inner array as well, and the structure becomes shareable.
- **Row 5.** `1`, `:a`, `nil`, `true`, `1.5` and `1..2` are frozen without anyone asking; a string literal is not — it is chilled, which the Ruby text library measures on its [literals are chilled ↗](https://masiarek.github.io/ruby-text-learning-library/05_Literals/literals_are_chilled/index.html) page — and an array literal is plainly mutable.
- **Row 6.** The same program run twice by a child Ruby. Without the comment, `"lit".frozen?` is `false` and `<<` works; with `# frozen_string_literal: true` on line 1, the literal is frozen and `<<` raises. The comment reaches every literal in that file and no further.
- **Row 7.** A frozen instance of your own class refuses its setter and `instance_variable_set` alike; there is no way around a frozen object short of `dup`.

## Compared with Python

Python has no `freeze`: an object is immutable or not by type, so the twin's rows use `tuple`, `frozenset`, `str`, `types.MappingProxyType` and a frozen dataclass. `copy.copy` of a tuple returns the very same object, since there is nothing to protect by copying (row 1). The refusals are ordinary `TypeError`s and `AttributeError`s — plain `Exception`s, with no frozen-specific class — whose messages this page does not key because CPython rewords them between releases (row 2). The shallowness is identical: a tuple holding a list lets the list grow (row 3), and there is no `make_shareable` — `MappingProxyType` is a read-only *view* of a dict whose values stay mutable and which reflects later changes to the dict, and `collections.abc.Hashable` is satisfied by `([1],)` even though `hash` of it fails, the same one-level check (row 4). What is born immutable is hashable — numbers, strings, `None`, `range` — and a list is neither (row 5); there is no magic comment because every string literal is immutable already, and `bytearray` is the mutable string when you need one (row 6). The back door is row 7: `dataclass(frozen=True)` raises `FrozenInstanceError` (an `AttributeError`) from `__setattr__`, but `object.__setattr__(c, "host", "x")` goes straight past it — Python's frozen is a convention enforced by one method, Ruby's is a flag the interpreter checks on every mutation.

```ruby
# Kata: deep_freeze freezes an object and, for arrays and hashes, everything
# inside it, recursively -- what a plain freeze leaves mutable.

def deep_freeze(obj)
  case obj
  when Array then obj.each { |e| deep_freeze(e) }
  when Hash then obj.each { |k, v| deep_freeze(k); deep_freeze(v) }
  end
  obj.freeze
end

config = { list: [1, [2]], name: "n" }
deep_freeze(config)
puts "   config.frozen?             #{config.frozen?}"
puts "   config[:list].frozen?      #{config[:list].frozen?}"
puts "   config[:list][1].frozen?   #{config[:list][1].frozen?}"
puts "   config[:name].frozen?      #{config[:name].frozen?}"

attempts = {
  "config[:list][1] << 3" => -> { config[:list][1] << 3 },
  "config[:name] << \"!\""  => -> { config[:name] << "!" },
  "config[:extra] = 1"     => -> { config[:extra] = 1 }
}
attempts.each do |label, attempt|
  attempt.call
  puts "   #{label.ljust(26)} worked"
rescue FrozenError => e
  puts "   #{label.ljust(26)} #{e.class}: #{e.message}"
end
puts "   Ractor.shareable?(config)  #{Ractor.shareable?(config)}"
```
