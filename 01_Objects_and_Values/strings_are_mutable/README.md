# Strings are mutable; `<<` keeps the object

**Level:** 101 · a Python programmer who has never had to ask whether a string changed underneath them

**One line:** A Ruby `String` is a mutable object — `<<`, `upcase!`, `[]=`, `insert`, `sub!` and `replace` change it in place and keep its identity, while `+`, `upcase` and `sub` return a new string — and a literal is chilled rather than frozen in Ruby 4.0; a Python `str` cannot change at all, so `+=` always rebinds and the mutable routes are `bytearray`, `io.StringIO` and a list joined at the end.

Ruby's string is a buffer with methods, and the buffer is the object. Every name that refers to it sees an in-place change, which is exactly the [reference semantics](../variables_are_references/README.md) of the previous page applied to text, and it is why `String` ships each operation twice: `upcase` returns a changed copy and leaves the receiver alone; `upcase!` changes the receiver and returns it — or `nil` when there was nothing to change, which is the trap in every chain of bang methods. `<<` appends without allocating a new object, which is what makes building a string in a loop cheap *(Not machine-checked here.)*, and it is also why Ruby has `freeze`, `# frozen_string_literal: true` and the "chilled" literal at all: a string that anyone may change is a string that needs protecting. The program prints six numbered groups, and the Python twin prints the same rows for an immutable `str`.

## Reading the output

- **Row 1.** `s << "d"` changes the string that `s` and `before` both name, and `equal?` stays `true`; `s += "e"` builds a new string and rebinds `s`, so `equal?` turns `false` and `before` keeps the appended `"abcd"`.
- **Row 2.** `upcase!` changed `u` in place and returned `u` itself; called on a string that is already upper case it returns `nil`, so a chain such as `str.upcase!.strip!` breaks when the first step has nothing to do *(Not machine-checked here.)*. The non-bang `upcase` returns a new object and leaves `v` as it was.
- **Row 3.** `[]=`, `insert`, `sub!`, `replace` and `clear` all edit the same object; `t` is one string throughout the group.
- **Row 4.** `"a".frozen?` is `false`: in Ruby 4.0 a literal is *chilled* — mutable, but flagged so that `-W:deprecated` warns when it is changed — and `lit << "!"` works. `+"a"` gives a mutable copy, `-"a"` the frozen, deduplicated one, and `String.new` a fresh buffer. The Ruby text library's [literals are chilled ↗](https://masiarek.github.io/ruby-text-learning-library/05_Literals/literals_are_chilled/index.html) page runs the warning and the magic comment five ways.
- **Row 5.** `<<` returns the receiver, so appends chain; a loop of `<<` grows one buffer; `join` and `chars`/`[]=`/`join` are the other two ways to build.
- **Row 6.** The cost of mutability, paid once per hash: a `String` key is copied and frozen on the way in, so `h.keys.first` is a different, frozen object and appending to the original `key` afterwards does not corrupt the lookup.

## Compared with Python

Python's `str` is immutable, and every row is the mirror image. `+=` rebinds — there is no `__iadd__` on `str` to do anything else — so `before` still reads `'abc'` after both appends (row 1). No method ends in `!` because none of them can change the receiver; `upper()` returns a copy every time (row 2). Item assignment is a `TypeError`, and each edit of row 3 is a rebinding to a new string built from slices. A literal is immutable like every other `str`, and `sys.intern` is the nearest thing to `-"a"` — one shared object per spelling — while there is nothing to correspond to `+"a"` (row 4). When you need a buffer, Python hands you a different type: `io.StringIO`, `bytearray` — the [Python library's page on it ↗](https://masiarek.github.io/python-learning-library/01_Text_and_Bytes/bytearray_is_mutable/index.html) — or a `list` of characters joined at the end (row 5). And a `dict` needs no copying trick, because a key that cannot change cannot break the table: the key in `d` is the very object, and `bytearray`, which can change, is refused as a key outright (row 6).

The other half of the comparison is what the two types *are*: Python separates text (`str`) from bytes (`bytes`), where a Ruby string is bytes plus an encoding label — the Python library's [`str` is not `bytes` ↗](https://masiarek.github.io/python-learning-library/01_Text_and_Bytes/str_is_not_bytes/index.html) and the Ruby text library's [a string is bytes plus a label ↗](https://masiarek.github.io/ruby-text-learning-library/01_Strings_Carry_an_Encoding/bytes_plus_a_label/index.html) measure that pair.

# Kata: censor! edits the caller's string in place with gsub!; censor returns
# a new string with gsub and leaves the original alone. equal? tells them
# apart, and the second censor! returns nil because nothing was left to change.

def censor!(text, word) = text.gsub!(word, "*" * word.length)
def censor(text, word) = text.gsub(word, "*" * word.length)

original = "the secret is a secret".dup
copy = censor(original, "secret")
puts "   censor returns            #{copy.inspect}"
puts "   original afterwards       #{original.inspect}"
puts "   copy.equal?(original)     #{copy.equal?(original)}"

result = censor!(original, "secret")
puts "   censor! returns           #{result.inspect}"
puts "   original afterwards       #{original.inspect}"
puts "   result.equal?(original)   #{result.equal?(original)}"
puts "   censor! a second time     #{censor!(original, "secret").inspect}"
