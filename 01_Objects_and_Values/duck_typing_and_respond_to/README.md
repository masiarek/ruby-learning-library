# Duck typing asks `respond_to?`, not `class`

**Level:** 201 · anyone who has written `if x.is_a?(Array)` and suspects there is a better question

**One line:** Ruby code asks an object what it can do — `respond_to?(:each)` — rather than what it is, and the core library does the same through the implicit conversions `to_str`, `to_ary`, `to_proc`, `to_int` and `to_path`, with `Array()` and `Integer()` as the strict conversions on request; Python asks with `hasattr`, with `isinstance` against an ABC or a `runtime_checkable` `Protocol`, and its `__iter__`, `__call__`, `__index__` and `__fspath__` are the same idea under other names.

In Ruby the type of an object is, for most purposes, the set of messages it answers. `respond_to?` asks that directly. `is_a?` asks about the ancestor chain, which includes modules, so a class that does `include Enumerable` *is* an `Enumerable` as well as acting like one; `instance_of?` asks for the exact class and is almost never the right question. The core library is the biggest duck-typer of all: `"a" + obj` works for anything with `to_str`, destructuring calls `to_ary`, `&obj` calls `to_proc`, an index calls `to_int`, `File` methods call `to_path` — and none of them call `to_s`, because "can be shown as text" is a weaker promise than "is text". For input you do not trust, `Array()` and `Integer()` convert strictly and loudly. The program prints six numbered groups, and the Python twin prints the same rows.

## Reading the output

- **Row 1.** Arrays, hashes and ranges answer `each`; a string does not — `String` has `each_char` but no `each`, because Ruby refuses to guess whether you meant characters, lines or bytes — and an integer does not either.
- **Row 2.** `is_a?` and `kind_of?` are one method under two names and walk the ancestors, so `1.is_a?(Numeric)` and `1.is_a?(Comparable)` are both `true`; `instance_of?` is `true` only for the object's own class.
- **Row 3.** A `Duck` and a `Robot` share no ancestor but both `quack`, so `respond_to?` lets both through and a `Rock` raises `NoMethodError` if you skip the check. The class test in the last line would have turned the `Robot` away.
- **Row 4.** One `each` plus `include Enumerable` gives `Countdown` `map`, `include?`, `sort` and the rest, and makes `is_a?(Enumerable)` true — without `Countdown` being an `Array` or holding one.
- **Row 5.** The implicit conversions: `String#+` asked `Name` for `to_str`, multiple assignment asked `Pair` for `to_ary`, `&` asked `Doubler` for `to_proc`, `Array#[]` asked `Idx` for `to_int`, and `File.basename` asked `Loc` for `to_path`. `Plain` offers only `to_s`, and `"x" + Plain.new` refuses it with a message worth memorising: `no implicit conversion of Plain into String`.
- **Row 6.** `Array()` wraps a non-array, unwraps `nil` to `[]` and turns a hash into pairs; `Integer()` parses strictly, raising `ArgumentError` on `"4x"` and `TypeError` on `nil`, where `"4x".to_i` shrugs and returns `4`. The Ruby text library's [`to_i` never fails ↗](https://masiarek.github.io/ruby-text-learning-library/07_Parsing_and_Formatting/to_i_never_fails/index.html) page follows that shrug.

## Compared with Python

Python's own [glossary ↗](https://docs.python.org/3/glossary.html#term-duck-typing) defines *duck-typing*, and the twin's rows are the same questions with other spellings. `hasattr(x, "__iter__")` is `respond_to?(:each)`, with one difference in the answers: a `str` is iterable in Python, character by character, where Ruby's `String` makes you choose `each_char` (row 1). `isinstance` walks the class hierarchy the way `is_a?` walks the ancestors, an abstract base class such as `Hashable` counts the way a module does, and `type(x) is int` is the exact-class test that `bool` fails (row 2). Python then goes one step further than Ruby: a `runtime_checkable` `Protocol` turns "has a `quack` method" into a type that `isinstance` can check, so the `Robot` passes a type test it never subscribed to (row 3). `__iter__` is `each`, but the toolkit arrives as builtin functions — `sorted(c)`, `2 in c`, a comprehension — rather than as methods mixed into the class, and `collections.abc.Iterable` plays the part of `Enumerable` for `isinstance` (row 4). The dunder protocols of row 5 map one to one — `__iter__` for `to_ary`, `__call__` for `to_proc`, `__index__` for `to_int`, `__fspath__` for `to_path` — except that Python has no implicit string conversion at all: `__str__` is consulted by `str()`, never by `+`, so `"Hello, " + Name("Ada")` needs the explicit `str()` (row 5). `list()` and `int()` are as strict as `Array()` and `Integer()`, and differ in three places: `list(1)` raises where `Array(1)` wraps, `list({"a": 1})` gives the keys where `Array({a: 1})` gives pairs, and there is no forgiving `to_i` at all — `int("4x")` is a `ValueError` and the polite check first is `isdigit()` (row 6).

```ruby
# Kata: a class with each and `include Enumerable` is a collection as far as
# every Enumerable method is concerned, without being an Array.

class Fibs
  include Enumerable

  def initialize(count) = @count = count

  def each
    return to_enum(:each) unless block_given?

    a, b = 0, 1
    @count.times do
      yield a
      a, b = b, a + b
    end
  end
end

fibs = Fibs.new(10)
puts "   to_a                 #{fibs.to_a.inspect}"
puts "   select(&:even?)      #{fibs.select(&:even?).inspect}"
puts "   each_slice(4).to_a   #{fibs.each_slice(4).to_a.inspect}"
puts "   include?(8)          #{fibs.include?(8)}"
puts "   first(3)             #{fibs.first(3).inspect}"
puts "   max                  #{fibs.max}"
puts "   respond_to?(:lazy)   #{fibs.respond_to?(:lazy)}"
puts "   is_a?(Array)         #{fibs.is_a?(Array)}"
puts "   Enumerable === fibs  #{Enumerable === fibs}"
```
