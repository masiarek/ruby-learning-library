# A string key and a symbol key are two keys

**Level:** 201 · anyone whose `config[:host]` came back `nil` after `JSON.parse`

**One line:** `{"a" => 1}[:a]` is `nil` because `"a"` and `:a` are different objects of different classes, `JSON.parse` always gives string keys, and the literal `{"a": 1}` — quotes, then a colon — makes a *symbol* key; Python has one string type, so `"a"` and `'a'` are the same key and the question never comes up.

A Hash finds a key by `eql?` and `hash`, and a `String` is never `eql?` to a `Symbol`. Ruby code written by hand uses symbol keys (`{host: "x"}`, keyword arguments, `fetch(:port)`); data that arrives from outside — JSON, YAML, CSV, a database row, `ENV` — comes with string keys, and the two meet at the boundary. `JSON.parse(text, symbolize_names: true)` or `transform_keys(&:to_sym)` converts on the way in; `to_json` converts symbols back to strings on the way out, so a round trip changes the key class. The trap for a Python reader is the literal `{"a": 1}`: the quotes look like a string key, but the colon after them makes a symbol, exactly as `{a: 1}` does, and Ruby quietly allows the quotes so that symbols with unusual characters (`{"a-b": 1}`) can be written. The program prints the lookups, both conversions, the trap, and the `KeyError` message that reveals which kind of key you asked for.

## Reading the output

- **Rows 1–2**: the same hash, asked with a symbol and with a string. Only the string finds the value; `key?` agrees.
- **Rows 3–4**: `JSON.parse` gives `String` keys; `symbolize_names: true` gives `Symbol` keys, all the way down.
- **Row 5**: `transform_keys` with `to_sym` or `to_s` converts a hash's keys in one call (one level only).
- **Row 6** is the trap: `{"a": 1}` inspects as `{a: 1}`, and its key is a `Symbol`.
- **Row 7**: a hash can hold `"a"` and `:a` side by side, as two entries. **Row 8**: two hashes that differ only in key class are not `==`.
- **Row 9**: `to_json` wrote `{"a":1}`, and parsing it back gave a `String` key — the round trip does not preserve symbols.
- **Row 10**: conversion both ways, and a reason to prefer symbols for fixed names: a symbol is always frozen, while a string literal is not.
- **Row 11**: quoting a symbol lets it hold a hyphen; `inspect` keeps the quotes so it can be read back.
- **Row 12**: `fetch` raises with the key in its message, `:a` with the colon — the fastest way to see which kind of key a lookup used.

## Compared with Python

Python has one string type, so rows 1–2 are the same lookup written with two quote styles, and row 6 is not a trap: `{"a": 1}` has a `str` key, as does every JSON object `json.loads` returns (rows 3–4), with no option to change that. Where Ruby chooses between two key kinds, Python chooses between `str` and any other hashable object — an `Enum` member is the closest thing to a symbol (row 5), a tuple is a valid key and a list is not (row 11), and `sys.intern` gives the identity-sharing that Ruby's symbols have by construction (row 10). Row 7 shows a literal with the same key twice keeps only the last value, and row 8 that an `Enum` key and its string value are different keys — so a program that mixes `Key.A` and `"a"` has the same bug Ruby programs have with `:a` and `"a"`, and row 12 is its `KeyError`. Row 9 is Python's version of the round-trip change: an `int` key becomes a `str` on the way through JSON, just as a Ruby symbol does.

```ruby
# Kata: symbolize every key in a nested structure, arrays included.
require "json"

def deep_symbolize(obj)
  case obj
  when Hash  then obj.to_h { |k, v| [k.to_sym, deep_symbolize(v)] }
  when Array then obj.map { |v| deep_symbolize(v) }
  else obj
  end
end

text = '{"user": {"name": "ann", "tags": ["x", "y"]}, "items": [{"id": 1}, {"id": 2}]}'
parsed = JSON.parse(text)

puts "before: #{parsed.inspect}"
puts "after:  #{deep_symbolize(parsed).inspect}"
puts "dig:    #{deep_symbolize(parsed).dig(:items, 1, :id)}"
puts "same as symbolize_names? #{deep_symbolize(parsed) == JSON.parse(text, symbolize_names: true)}"
```
