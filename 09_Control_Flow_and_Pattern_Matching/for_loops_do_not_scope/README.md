# `for` loops do not make a scope

**Level:** 201 · a Python programmer who reaches for `for`, and a Ruby programmer who wonders why nobody else does

**One line:** `for` and `while` are syntax and open no scope — the loop variable and anything first assigned in the body are still there afterwards — while a block is a scope of its own, which is why Ruby code says `each`; Python's `for` and `while` leak the same way, its only scoped loop is a comprehension, and a function is where a temporary lives.

`for x in collection` is `collection.each` in disguise: it calls `each` and assigns each yielded value to `x` — but `x` is a variable of the *enclosing* scope, as is every variable the body assigns, so they all survive the loop, and an empty collection still leaves `x` defined, because the parser saw the assignment. `while` and `until` are the same: no scope. A block is different. Its parameters are new variables that exist only inside it, and a local first assigned inside it is a block-local too; only names that already existed outside are shared, and those the block can read and assign. That difference is why the idiomatic loop is `each`, `times`, `upto`, `step` or `loop` with a block: nothing leaks, and a lambda created inside sees its own iteration's value rather than a shared variable's last one. The program leaves each kind of loop behind and looks at what is still defined.

## Reading the output

Row 1: after `for i in 1..3; x = i; end`, both `i` and `x` are still defined, holding `3`. Row 2: after `[10, 20].each { |j| y = j }`, `defined?(j)` is `nil` and reading `y` is a `NameError` — the block parameter and the block-local both ended with the block. Row 3: `for` really did call `Bag#each`, and `v` is still there afterwards, holding the last yielded value. Row 4: `while` leaks `w` just as `for` leaks `x`.

Row 5: the block-taking iterators — `times`, `upto`, `step`, `loop` — leave nothing behind, while `loop` was still able to count in the outer `k`, which row 6 states directly: a block reads and assigns a variable that already exists outside it, and only *new* names are local to it. Row 7: `for a, b in pairs` destructures, and both names leak. Row 8: `for` is an expression like everything else — its value is the collection it iterated, or the argument of a `break`. Row 9 is the escape hatch for a name clash: `|q; outer|` declares `outer` block-local, so the assignment inside shadowed the outer `outer` instead of overwriting it. Row 10: even `for none in []`, which never runs its body, leaves `none` defined, holding `nil`. Row 11 is the practical consequence: three lambdas made in a `for` loop all return `3`, because they closed over the one shared `c`, while three made in `each` return `1, 2, 3`, because each block call had its own `d`.

## Compared with Python

Python's `for` and `while` behave like Ruby's: `i`, `x` and `w` survive (rows 1 and 4), `for` calls `__iter__` where Ruby calls `each` (row 3), a destructuring `for a, b` leaks both (row 7), and lambdas made in a `for` all see the last value (row 11) — the classic late-binding trap, which a comprehension does *not* fix, because the comprehension's variable is also one variable; the `lambda d=d` default is the fix. Where Python differs is in what it offers as a scope. It has no blocks; its one scoped loop is the comprehension, whose variable is gone afterwards (row 2) and which shadows rather than assigns an outer name (row 9, the twin of Ruby's `|q; outer|`). For everything else the scope is a function (row 5) — with the mirror-image rule of row 6: a loop at module level assigns the module's `z`, but an assignment inside a `def` creates a new local (unless the name is declared `global` or `nonlocal` *(Not machine-checked here.)*). Two smaller differences: `for` is a statement with no value (row 8), and the leaked name can be removed with `del`; and an empty loop never binds its variable at all (row 10), where Ruby's parser had already created it.
