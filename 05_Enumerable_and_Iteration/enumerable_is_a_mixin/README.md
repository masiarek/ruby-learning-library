# Enumerable is a mixin: write `each`, get the rest

**Level:** 201 · a Python programmer who has written `__iter__` and wonders where Ruby's `map` lives

**One line:** A class that defines `each` and says `include Enumerable` gains `map`, `select`, `sort_by`, `min_by`, `include?`, `first`, `each_slice`, `lazy` and fifty-odd more, because Ruby keeps the toolbox in a module that is mixed into the class, where Python keeps it in builtins and `itertools` and only `collections.abc.Sequence` plays the same trick.

Ruby's collection methods are not defined on `Array` and copied to `Hash`, `Range`, `Struct`, `Set`, `Dir` and `Enumerator`: they are defined once, in the module `Enumerable`, in terms of one method the module does not define — `each`. A class that writes `each` and includes the module gets every other method for the price of one line, and the module has no idea what it is iterating, only that `each` will yield the items one at a time. `Shelf` below is the whole recipe: an `each` that yields (and returns an Enumerator when called without a block, so `shelf.each.next` works too), plus `include Enumerable`. `Bare` is the same class without the include, to show that `each` on its own buys nothing.

## Reading the output

Rows 1–4: `Bare` has an `each` but no `map`: `respond_to?(:map)` is `false` and calling it raises `NoMethodError`. `Shelf` differs by one line, and its ancestor chain shows where the methods come from — `Enumerable` sits between the class and `Object`, so a call to `shelf.map` misses in `Shelf`, hits in `Enumerable`, and the module's `map` calls `shelf.each` to get the items.

Rows 5–17: a handful of what arrived. `map`, `select`, `sort_by`, `min_by`, `include?`, `first`, `each_slice`, `to_a`, `each_with_index`, `sum` and `lazy` all work on a class that only knows how to yield four strings. Row 17 is the `to_enum` guard paying off: `each` without a block returns an `Enumerator`, and `next` pulls the first title — the [external enumerators](../external_enumerators/README.md) page is about that object.

Rows 18–26: the core classes that include the module. `Array`, `Hash`, `Range`, `Struct`, `Dir`, `Set` and `Enumerator` do; `String` and `Integer` do not. A Ruby string is not a collection of anything until you ask for `each_char`, `each_byte` or `each_line`, each of which returns an Enumerator that is *(Not machine-checked here.)*.

Rows 27–31: the module from its own side. `Enumerable.instance_methods` does not include `each` (row 27) — that is the one method the includer supplies — but it does include `tally`, and there are more than fifty of them (row 28 prints a comparison rather than the count, which is version-sized). Row 29 is worth a look: `Array` overrides `map` with its own version (its owner is `Array`) but leaves `inject` to the module (owner `Enumerable`), so the same call on an Array and on a Shelf may run different code and give the same answer. Rows 30–31 show the other standard mixin, `Comparable`: define `<=>`, include it, and `<`, `<=`, `==`, `>`, `>=`, `between?` and `clamp` arrive the same way — and `Shelf` does not have them, because a mixin is opt-in, one `include` at a time.

## Compared with Python

Python has no module to include. An object with `__iter__` *is* iterable, and that is the whole protocol: `isinstance(shelf, Iterable)` is `True` in row 3 without `Shelf` inheriting from anything, because `collections.abc.Iterable` recognises the method by duck typing. But nothing arrives on the object — `hasattr(shelf, "map")` is `False` in rows 1 and 4 and stays `False`. The toolbox is elsewhere: `map`, `sorted`, `min`, `enumerate` and `sum` are builtins that *take* an iterable, `islice` and `batched` live in `itertools`, and `[t for t in shelf if …]` is syntax. Rows 5–17 are the same handful in that form; row 14 is a real difference (`sum` refuses strings and the fix is `"".join`), and row 15 shows that Python's `map` is lazy already — an iterator, not a list — so there is no `.lazy` to call.

Rows 18–26 put the same builtins to the ABC. Every container answers `True`, and so does `"abc"`: a Python `str` iterates its characters, where Ruby's `String` is not Enumerable at all. Rows 27–31 are Python's one real mixin. `Iterable` asks for a single method, `__iter__`, and gives back nothing but the `isinstance` check; `collections.abc.Sequence` asks for two, `__getitem__` and `__len__`, and `Deck` — which defines exactly those — gets `in`, `index`, `count` and `reversed` for free in row 31. That is Ruby's `Enumerable` mechanism, applied to sequences only.

```ruby
# Kata: a Fibonacci sequence that stops at a limit, made Enumerable by one `each`.
class Fib
  include Enumerable

  def initialize(limit) = @limit = limit

  def each
    return to_enum(:each) unless block_given?
    a, b = 0, 1
    while a <= @limit
      yield a
      a, b = b, a + b
    end
    self
  end
end

def row(n, label, value) = puts(format("%2d. %-42s %s", n, label, value.inspect))

fib = Fib.new(100)
row 1, "to_a", fib.to_a
row 2, "select(&:even?)", fib.select(&:even?)
row 3, "each_cons(2).map { |a, b| b - a }", fib.each_cons(2).map { |a, b| b - a }
row 4, "include?(21), include?(22)", [fib.include?(21), fib.include?(22)]
row 5, "sum", fib.sum
row 6, "min_by { |x| (x - 50).abs }", fib.min_by { |x| (x - 50).abs }
row 7, "each_slice(4).to_a", fib.each_slice(4).to_a
row 8, "each.class, each.next", [fib.each.class, fib.each.next]
row 9, "lazy.map { |x| x * x }.first(3)", fib.lazy.map { |x| x * x }.first(3)
row 10, "each_with_index.select { |x, i| x == i }", fib.each_with_index.select { |x, i| x == i }.map(&:first)
```
