# `sort_by` keys once, `sort` many times, neither is stable

**Level:** 201 · anyone who has sorted records by one field and been surprised by the order of the ties

**One line:** `sort_by` computes each element's key exactly once and `sort { |a, b| … }` recomputes at every comparison, but Ruby promises neither the order of equal keys — the docs say it is indeterminate and may be unstable — so the portable idioms are a composite key such as `[age, name]` or the index trick `sort_by.with_index { |x, i| [key, i] }`, where Python's `sorted` is guaranteed stable, `reverse=True` included.

`sort_by { |x| key }` runs the block once per element, pairs each element with its key, sorts the pairs and unwraps them — the Schwartzian transform, and the reason it beats `sort { |a, b| key(a) <=> key(b) }` whenever the key costs anything: a sort compares each element many times and the block form pays for the key at every comparison. What neither form promises is what happens to elements whose keys compare equal. Ruby's documentation for `sort_by` says that the ordering of equal elements is indeterminate and may be unstable, and in practice Ruby's `sort` uses the C library's `qsort_r` where the platform has one, so the tie order — and the number of comparisons — differ between Linux and macOS *(Not machine-checked here: this page prints checks and stable idioms, never a raw tie order, precisely because the answer key must be identical on both)*.

## Reading the output

Rows 1–3 count the work. `sort_by` called its block exactly eight times for eight words (row 1) and the result is fully ordered because the key `[size, word]` never ties. The `sort` with a block reached the same order (row 2, `same result: true`) but computed keys at least `2 × (n − 1)` times, and its block ran at least `n − 1` times (row 3) — the lower bound any comparison sort must meet. The page prints those as checks because the exact counts depend on the platform's sort routine; on the Mac that recorded this page the block form computed the key four and a half times as often as `sort_by` *(Not machine-checked here.)*.

Rows 4–7 are ties. Row 4 prints only what `sort_by(&:age)` promises: the ages come out non-decreasing and the same six people are present — and deliberately not the names, because two 25-year-olds and three 30-year-olds may come out in any order, and the order this Mac produced is not the order Ubuntu produces. Row 5 is the stable idiom: `sort_by.with_index { |p, i| [p.age, i] }` breaks every tie by original position, so `Bob` stays before `Abe` and `Ann, Cid, Fay` keep their order. Row 6 breaks ties by a second field instead, and now `Abe` precedes `Bob`. Row 7 is the descending trap: `[-p.age, i]` keeps ties in input order within each age, but `reverse` on the stable ascending result reverses the ties as well — `Fay, Cid, Ann` — which is rarely what a report wants.

Rows 8–11: `sort` returns a new array and `sort!` sorts the receiver (row 8, `equal?` false then true). Three spellings of descending agree on distinct values (row 9), and `max(2)` is the cheap way to the top two. Mixed types cannot be compared, and the error is `ArgumentError` (row 10) — its message names the two operands in the order the algorithm happened to compare them, which is platform-dependent, so only the class is printed. A block that returns `nil` instead of `-1`, `0` or `1` is the same `ArgumentError` (row 11).

Rows 12–16: `min_by` and `max_by` are single passes, not sorts. Strings sort by code point, so `"C"` precedes `"a"` until `sort_by(&:downcase)` (row 13); numeric strings need `sort_by(&:to_i)` (row 14); `sort_by!` sorts in place and is an `Array` method — `Enumerable` has no bang version, as row 15 also prints; and `sort_by` on a Hash yields `|key, value|` pairs and returns an array of pairs, which `to_h` turns back into a Hash (row 16).

## Compared with Python

Python's `sorted` and `list.sort` are documented as stable, and the twin prints what that buys. Row 1 is the same as Ruby's: the key runs exactly once per element. Row 2 uses `functools.cmp_to_key` for the comparison-function style, and row 3 is a check for the same reason as in Ruby — on the machine that recorded this page the comparison count differed between Python 3.12 and 3.14 for this very input, fifteen against seventeen *(Not machine-checked here.)*. Row 4 is where the languages part: because the order is guaranteed, the twin prints the names, and they are the input order within each age — the index idiom of row 5 gives the same answer and is redundant in Python. `attrgetter("age", "name")` is the composite key (row 6), and `reverse=True` keeps ties in *input* order, unlike `reversed()` on the ascending result (row 7) — the documentation promises exactly that. Stability also lets Python compose sorts, sorting by the secondary key first and by the primary key second; a Ruby program that does the same is relying on something Ruby does not promise *(Not machine-checked here.)*.

The rest lines up: `sorted` returns a new list and `list.sort` returns `None` (row 8), which is why `xs = xs.sort()` is a classic mistake; `TypeError` for mixed types and for a comparison function that returns `None` (rows 10–11); `min`/`max` with `key=`; code-point order for strings and `key=str.lower` (row 13) — the Python library's [Sorting is not comparing ↗](https://masiarek.github.io/python-learning-library/01_Text_and_Bytes/sorting_is_not_comparing/index.html) is about why code-point order is no human alphabet; `key=int` for numeric strings; `sort(key=)` in place, on a list only (a tuple has no `sort`, row 15); and `sorted(d.items(), key=itemgetter(1))` for a hash by value.

## Try it

1. Given `[["Ann", 30], ["Bob", 25], ["Cid", 30], ["Abe", 25], ["Eve", 41]]`, print six orderings, none of which may depend on how `sort` breaks ties: by age with ties in input order (the index idiom), by age descending then name ascending, the same with `sort` and a block, the names by length then alphabetically, the ages from a plain `sort_by { age }` together with a check that they are valid, and a demonstration that `sort` returns a new array while `sort!` returns the same one.
2. Count the key computations of `sort_by { key }` and of `sort { key(a) <=> key(b) }` on arrays of 10, 100 and 1000 numbers from `Random.new(1)`. How does the second count grow relative to the first? Do not record the exact counts as an answer key — they depend on the platform's sort routine — record the ratio's rough size instead.

```ruby
# Kata: six orderings of one list, none of which depends on how sort breaks ties.
def row(n, label, value) = puts(format("%2d. %-46s %s", n, label, value.inspect))

people = [["Ann", 30], ["Bob", 25], ["Cid", 30], ["Abe", 25], ["Eve", 41]]

row 1, "by age, ties in input order (with_index)", people.sort_by.with_index { |(_, age), i| [age, i] }.map(&:first)
row 2, "by age descending, then name ascending", people.sort_by { |name, age| [-age, name] }.map(&:first)
row 3, "the same with sort and a block", people.sort { |a, b| (b[1] <=> a[1]).nonzero? || (a[0] <=> b[0]) }.map(&:first)
row 4, "names by length, then alphabetically", people.map(&:first).sort_by { |n| [n.size, n] }
ages = people.sort_by { |_, age| age }.map(&:last)
row 5, "sort_by { age }: the ages, and are they valid?", [ages, ages.each_cons(2).all? { |a, b| a <= b }]
names = people.map(&:first)
row 6, "sort returns a new array; sort! the same one", [names.sort.equal?(names), names.sort!.equal?(names)]
```
