# An Enumerator has a cursor: `next`, `peek`, `rewind`

**Level:** 201 · a Python programmer who knows `iter()` and `next()` and wants the Ruby spelling, plus the two things Ruby adds

**One line:** Any `each` called without a block returns an `Enumerator`; `next` pulls one value from it, `peek` looks at the next one without taking it, `StopIteration` marks the end and carries the iteration's return value in `result`, `rewind` starts over and `loop` rescues `StopIteration` for you — where Python's iterators have `next()` and `StopIteration` only, no peek, no rewind, and one cursor that a `for` loop shares.

Internal iteration hands each element to a block and keeps control; external iteration gives control to the caller, who asks for elements one at a time — which is what you need to walk two collections in step (the kata merges two sorted arrays that way), to read a header before the body, or to hand a half-consumed sequence to someone else. Ruby keeps the two kinds apart: the cursor that `next` moves belongs to the Enumerator object, and the same object's `to_a`, `map` or `each` start from the beginning without touching it, because `next` runs the underlying `each` on a fiber that is suspended between calls — the [enumerators run on fibers](../../12_Concurrency_and_Parallelism/enumerators_run_on_fibers/README.md) page measures that; here it is only the reason *(Not machine-checked here.)*.

## Reading the output

Rows 1–8, the cursor: `each` with no block returns an `Enumerator`; `next` gives `1`; `peek` shows `2` and leaves it there, so the following `next` gives `2` too. At the end `next` raises `StopIteration` with the message `iteration reached an end`, and the exception carries `result` — the value the underlying `each` returned, which for an Array is the Array itself (row 5). An exhausted enumerator stays exhausted (row 6) until `rewind` (row 7). Row 8 is `size`, answered without iterating: `2` for an array's `each`, `Infinity` for `cycle`, and `nil` for a hand-built `Enumerator.new` that was given no size.

Row 9 is the idiom that makes external iteration pleasant: `loop` rescues `StopIteration` silently, and its own value is the exception's `result`, so `loop { e.next }` walks an enumerator to the end and returns what `each` returned (`equal?(arr)` is `true`). Rows 10–11 are the separation of cursors: after one `next`, `to_a` returns all three elements from the start, and the next `next` still returns the second element — internal iteration never moved the cursor. `with_index(1)` chains onto any enumerator.

Rows 12–18, enumerators built by hand: `Enumerator.new` gets a yielder, `y << v` and `y.yield v` both hand a value out, and the block's own value becomes the `result` (row 12: `:done`). A method turned into an enumerator with `to_enum` (row 13) behaves the same — `loop { em.next }` returns the method's return value. An exception raised inside the block comes out of the `next` that ran it (row 14). `Enumerator.produce` makes an endless enumerator from a seed and a step (row 15), and every blockless iterator method is an enumerator source — `3.times`, `each_char`, `Hash#each` (row 16). Row 17 places `StopIteration` in the hierarchy: under `IndexError`, so a bare `rescue` catches it, which is what `loop` does. Row 18: `peek` on an exhausted enumerator raises the same way `next` does.

## Compared with Python

`iter(x)` and `next(it)` are the same protocol, and the twin's rows line up until Ruby adds something. There is no `peek` (row 3): the standard-library answers are `itertools.tee` or a one-item buffer, and the third-party `more-itertools` package's `peekable` *(Not machine-checked here.)*. There is no `rewind` (row 7): `iter(it) is it`, an iterator's `__iter__` returns itself, so the only way back to the start is a fresh `iter(x)`. `StopIteration.value` is `None` for a list iterator (row 5) but holds a generator's `return` value (row 12) — and `yield from` captures it inside another generator (row 13), where a `for` loop or `list()` throws it away. `next(it, default)` is the Python spelling for "or stop", and `operator.length_hint` is the polite question about size: `2` for a list iterator, `0` for `count()`, a hint rather than a size, while `len` refuses (row 8).

The one real difference is the cursor. A `for` loop catches `StopIteration` silently like Ruby's `loop` (row 9, though as a statement it has no value to return), but it drives the *same* cursor: in row 10, `list(it3)` after one `next` returns only the two remaining elements and leaves the iterator exhausted, where Ruby's `to_a` started over and left the cursor alone. In Python an iterator is a position; in Ruby an Enumerator is a recipe with a position attached. `produce` is a three-line generator (row 15); every container gives an iterator through `iter()` (row 16); `StopIteration` derives from `Exception` (row 17), so `except Exception` catches it — and, by PEP 479, a `StopIteration` raised *inside* a generator body is turned into `RuntimeError` rather than ending the generator *(Not machine-checked here.)*.

```ruby
# Kata: merge two sorted arrays, and interleave two arrays of different lengths,
# with nothing but external enumerators: next, peek and StopIteration.
def row(n, label, value) = puts(format("%2d. %-44s %s", n, label, value.inspect))

def merge(a, b)
  ea, eb = a.each, b.each
  out = []
  loop { out << (ea.peek <= eb.peek ? ea.next : eb.next) }   # ends when either peek raises StopIteration
  loop { out << ea.next }                                    # drain whichever side is left...
  loop { out << eb.next }                                    # ...the other loop ends at once
  out
end

def interleave(a, b)
  ea, eb = a.each, b.each
  out = []
  loop do
    out << ea.next
    out << eb.next
  end
  loop { out << ea.next }
  loop { out << eb.next }
  out
end

row 1, "merge([1, 4, 9], [2, 3, 10, 11])", merge([1, 4, 9], [2, 3, 10, 11])
row 2, "merge([], [5, 6])", merge([], [5, 6])
row 3, "interleave(%w[a b c], [1, 2])", interleave(%w[a b c], [1, 2])
row 4, "interleave([1], %w[x y z])", interleave([1], %w[x y z])
e = [1, 2, 3].each
e.next
row 5, "the trap: to_a after next starts over", [e.to_a, e.next]
```
