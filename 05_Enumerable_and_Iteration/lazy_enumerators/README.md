# `lazy` runs the chain one element at a time

**Level:** 201 · a Python programmer who thinks of `map` as a generator and wants to know why Ruby's returns an array

**One line:** `map` and `select` on an ordinary collection each run to the end and build an array before the next stage starts; `lazy` turns the same chain into an `Enumerator::Lazy` that pulls one element through every block only when a consumer such as `first(n)` asks — which is how an endless range can be mapped — and that is what Python's generators, `map` and `filter` do without being asked.

An eager chain is a sequence of whole arrays: `(1..4).map { }` produces four values, and only then does `select` look at them. A lazy chain is a pipeline: each adapter — `map`, `select`, `take_while`, `each_slice`, `filter_map`, `with_index`, `zip`, `uniq`, `flat_map`, `drop_while`, `take` — returns another `Enumerator::Lazy` that remembers what to do and does nothing, and a consumer — `first(n)`, `to_a` (also spelled `force`), `include?`, `sum`, `find`, `next` — pulls elements through the whole pipeline one at a time and stops as soon as it has its answer. Two things follow: the blocks run interleaved, and the source may be endless. The trace lines under the two headings print the blocks in the order they ran.

## Reading the output

The two traces are the lesson. Eager: `map(1) map(2) map(3) map(4)`, then `select(10) select(20) select(30) select(40)` — every stage finishes before the next starts, and row 1 holds all three hits. Lazy: `map(1) select(10) map(2) select(20) map(3) select(30)` — each element goes through both blocks before the next element is touched, and because `first(2)` had its two hits after `select(30)`, `map(4)` never ran. Same blocks, same answer for the first two, a different order and a different amount of work.

Rows 3–12 are the endless sources: `(1..Float::INFINITY)` and its shorter spelling, the endless range `(1..)`. An eager `map` over either would never return; the lazy chain in row 3 finds the first three doubled numbers divisible by three, and row 4 counts what it cost — nine calls of the `map` block, because the hits are at 3, 6 and 9. Rows 5–12 are the adapters that keep a chain lazy: `take_while`, `each_slice`, `filter_map`, `with_index`, `zip`, `uniq` (which must remember what it has seen), `flat_map`, `drop_while`.

Rows 13–20 sort the methods into the two kinds. Every adapter returns another `Enumerator::Lazy` (row 13), and `take(2)` is an adapter where `first(2)` is a consumer that returns an Array (row 14) — so `take(3)` needs a `force` or `to_a` to produce anything (row 15). `eager` goes the other way: it wraps the lazy chain in an ordinary `Enumerator`, whose `map` builds an Array again (row 16). A consumer that can stop early still stops on an endless source (`include?(5)` in row 17), and `sum` on a finite one runs the chain to the end. Row 18 is `size`: `(1..).lazy.size` is `Infinity`, a lazy `map` keeps its source's size, and a lazy `select` reports `nil` because nobody can know how many elements will pass without running it. Row 19 is worth remembering: a `Lazy` is an `Enumerator` (row 20 shows the ancestry), so `next` pulls values from it one at a time — the [external enumerators](../external_enumerators/README.md) page — and the two ideas, laziness and external iteration, are one object.

## Compared with Python

Python's chains are lazy unless you ask for a list. A generator expression `(f(x) for x in xs)` is Ruby's `lazy.map`, one with an `if` is `lazy.select` or `lazy.filter_map`, and the builtins `map` and `filter` return iterators too, so the trace under the second heading interleaves exactly as Ruby's did and stops after the second hit. The eager spelling is the list comprehension: the trace under the first heading, all maps then all selects, comes from two of them. `itertools.islice(chain, n)` is `first(n)` (but returns another iterator, so `list(...)` is the consumer), `itertools.count(1)` is `(1..)`, `batched` is `each_slice`, `takewhile` and `dropwhile` are named the same, `enumerate` is `with_index`, `zip` pairs two sources, and `chain.from_iterable` is `flat_map`. Row 10 is the one adapter Python lacks: there is no lazy `uniq` in the standard library, so the twin writes a four-line generator with a seen-set.

Rows 13–20 read the other way round. There is no `.lazy` to call — `generator`, `map` and `filter` are the types of the lazy objects (row 13) — and no `.eager` either: `list(...)` or a comprehension is how a chain is run (rows 14–16). `in` stops early on `count(1)` just as `include?` did (row 17). `len` refuses an iterator with `TypeError`, and `operator.length_hint` is the polite question: it answers `3` for a list iterator and `0` for a `map`, which does not propagate its input's length (row 18) — Ruby's lazy `map` keeps the size and its `select` says `nil`. And row 19 is the same fact as in Ruby: the generator that is the lazy pipeline is also the object that `next` drives.

Print the first ten primes and the count, the first prime above 1000 and the count, the primes in slices of three, the first four twin-prime pairs (`each_cons(2)` plus `select`), the prime squares below 200 (`map` plus `take_while`), and the hundredth prime (`with_index(1)` plus `find`).
