# `new` is `allocate` then `initialize`

**Level:** 201 · anyone who has written `def initialize` and wondered who calls it

**One line:** `Point.new(1, 2)` is a class method that does two things — `Class#allocate` makes an empty object, then the automatically private instance method `initialize(1, 2)` fills it in — so `allocate` alone gives you an object with no instance variables, `initialize`'s return value is ignored, and overriding `self.new` lets a class cache or dispatch its instances before any of that happens.

There is no constructor syntax in Ruby. `new` is an ordinary method on `Class`, which every class object inherits, and `initialize` is an ordinary instance method that `new` calls for you — it has to, because Ruby makes `initialize` private without being asked (along with `initialize_copy`). Everything the program below prints follows from that: what you can call on a freshly `allocate`d object, why `pt.initialize` raises, why an `ArgumentError` from `new` names `initialize`'s arity, and why `super` inside a `self.new` override is the only thing that ever runs `initialize`.

## Reading the output

- **1.** `Point.new(1, 2)` prints the trace from inside `initialize` and returns the finished object. Both `new` and `allocate` are owned by `Class`, not by `Point`.
- **2.** `private_instance_methods(false)` lists `initialize` and `initialize_copy`, neither of which was declared private: Ruby makes them so. Calling `pt.initialize(3, 4)` from outside is therefore a `NoMethodError`, while `send` reaches it and re-initialises the object in place — see [`send` and `public_send`](../../10_Metaprogramming/send_and_public_send/README.md).
- **3.** `Point.allocate` returns a `Point` with no instance variables, so its reader `x` is `nil`. A second `send(:initialize, 5, 6)` turns it into a normal point. This is what `Marshal.load` and object-relational mappers do: allocate, then fill in the state from elsewhere. *(Not machine-checked here.)*
- **4.** `initialize` returns `:the_return_value_is_ignored`; `new` still returns the object, so `Point.new(0, 0).class` is `Point`.
- **5.** `new` passes its arguments straight through, so the `ArgumentError` names `initialize`'s expectation: `given 1, expected 2`.
- **6.** `Color.new` is overridden to look in a cache first. `super` is what reaches `Class#new`, so `initialize` runs once per colour: the trace shows `"red"` initialised once even though `Color.new("red")` was called twice, and the two calls return the same object (`equal?` is `true`).
- **7.** `Shape.new(:circle, 3)` dispatches to a subclass's `new`; the subclasses fall through to `super`, so `Circle.new(5)` still works directly.
- **8.** `dup` and `clone` do not call `initialize`. They call `initialize_copy` on the new object with the original as the argument — the hook to deep-copy a field. [dup, clone and frozen state](../dup_clone_and_frozen_state/README.md) measures the rest.
- **9.** Some classes opt out. `Integer.allocate` raises `TypeError: allocator undefined for Integer`, and `Integer.new` and `NilClass.new` are `NoMethodError`s: those classes undefine `new`, because integers are immediates and `nil` is the one instance of its class.
- **10.** A subclass's `initialize` calls `super(x, y)` explicitly; `arity` is `3`, the subclass's own signature.

## Compared with Python

Python splits the same two steps into two dunder methods and runs them from the metaclass: `Point(1, 2)` is `type.__call__(Point, 1, 2)`, which calls `Point.__new__(Point, 1, 2)` — inherited from `object` here — and then `__init__(1, 2)` on the result. Row 2 is the first difference: `__init__` is public, so `pt.__init__(3, 4)` simply re-initialises the object, and Python has no private methods for `new` to need `send` for. Row 3 is `allocate` by another name: `object.__new__(Point)` skips `__init__`, leaves `vars(blank)` empty, and a later `blank.__init__(5, 6)` fills it. Row 4 is a difference in the other direction — `__init__` must return `None`, and returning `5` is a `TypeError`, where Ruby ignores `initialize`'s value. Row 6 is the trap: a cache written in `__new__` returns the cached object, but `type.__call__` then runs `__init__` on it *again* — the trace shows `Color.__init__('red')` twice — because `__init__` runs whenever `__new__` returns an instance of the class; Ruby's `self.new` override never calls `initialize` unless `super` does. Row 7's factory works in both, and for the same reason: `__new__` returning a `Circle` (an instance of `Shape`) still gets `__init__`. Row 8: `copy.copy` calls `__copy__` when the class defines it, and never `__init__` — Ruby's `initialize_copy` is the same hook by another name, and `copy.deepcopy` falls back to a state copy when there is no `__deepcopy__`. Row 9: `object(1)` and `int.__new__(str)` are `TypeError`s, and `type(None)()` hands back the one `None` rather than building a second one.

```ruby
# Exercise 1: a shared zero. Money.new(0) always returns one object, built once;
# every other amount is a fresh object. Count how often initialize runs, then
# show that allocate walks around the override entirely.

class Money
  @built = 0

  class << self
    attr_reader :built

    def new(cents)
      return @zero ||= super if cents.zero?
      super
    end

    def count_one = @built += 1
  end

  attr_reader :cents

  def initialize(cents)
    Money.count_one
    @cents = cents
  end

  def inspect = "#<Money #{@cents}c>"
end

zero_a = Money.new(0)
zero_b = Money.new(0)
five_a = Money.new(5)
five_b = Money.new(5)

puts "Money.new(0)                        #{zero_a.inspect}"
puts "Money.new(0).equal?(Money.new(0))   #{zero_a.equal?(zero_b)}"
puts "Money.new(5).equal?(Money.new(5))   #{five_a.equal?(five_b)}"
puts "times initialize ran                #{Money.built}"
puts "Money.allocate.cents                #{Money.allocate.cents.inspect}"
puts "times initialize ran after allocate #{Money.built}"
```
