# `Class.new` makes a class; a constant names it

**Level:** 301 · for a reader who knows `class Foo; end` and wants to build classes from data, in a loop or inside a method

**One line:** `Class.new(Base) { ... }` returns a class object with no name, `Foo = klass` gives it the name of the first constant it is assigned to, and `const_set` does the same under a module — while Python's `type("Foo", (Base,), {...})` names the class at birth, so there is no anonymous phase and no first-name-sticks rule.

`class Dog < Animal; ...; end` does three things: it creates a `Class` object, runs the body with that class as `self`, and assigns the object to the constant `Dog`. `Class.new(Animal) { ... }` does the first two — the block is run with `class_eval`, so `def` inside it defines instance methods and the block is a closure over the surrounding locals — and leaves the third to you. Until a constant holds it, the class's `name` is `nil`; the first constant assignment sets the name permanently, and later aliases do not change it. `Module.new` makes a module the same way, `Struct.new` and `Data.define` are class factories built on the same primitive, and `Object.const_set(:Name, klass)` is the programmatic form of `Name = klass`, including under a module (`Zoo.const_set(:Cat, ...)` gives `"Zoo::Cat"`). What you cannot do: subclass `Class` itself, or use a module as a superclass, or name a class with anything but a constant. The program measures each of these and the two facts that follow — `inherited` fires before the name exists, and a `Class.new` inside a method makes a fresh class on every call.

## Reading the output

Rows 1–4 are the naming rule: the class works before it has a name (row 1), `name` is `nil` (row 2), `Dog = k` names it (row 3), and `Hound = Dog` is just a second constant for the same object, whose name stays `Dog` (row 4). Row 5 is the same rule through `const_set` under a module, and `const_get` with a `"Zoo::Cat"` string walks the path back. Row 6: modules are made and named the same way, and an anonymous module can be included before it has a name. Row 7: `Struct.new` and `Data.define` are `Class.new` with a body written for you. Row 8 locates the class in the object model — it is an instance of `Class`, which is a `Module`, and a `Class.new` with no argument extends `Object`. Row 9 is the timing consequence for the [`inherited` hook](../hooks_inherited_included_method_added/README.md): `Class.new(Animal)` fired it with a nameless subclass, `class Kitten < Animal` with a named one. Row 10: the block is a closure, so `define_method` inside it can use `factor`. Row 11 draws the limits — `Class.new(Class)` is refused (there are no metaclasses in Ruby; singleton classes take that role) and a module cannot be a superclass. Row 12: a constant name must be capitalised, so `const_set(:lower, ...)` is a `NameError`. Row 13: `remove_const` takes a name away again (it is private — hence `send`) and returns the class, which lives on unnamed. Row 14: `Class.new` inside a method returns a different class each time, each one anonymous, which is how test suites make throwaway classes. Row 15 is a difference the Python twin fills in.

## Compared with Python

Python's three-argument `type(name, bases, namespace)` is `Class.new` with the name supplied up front, so rows 2–4 collapse: a class is named at birth, an empty string is an acceptable name, assignment to a variable changes nothing, and `__name__` is simply a writable attribute. Row 5 shows the other half of the naming model: `__qualname__` and `__module__` are set when the class is made and do not follow it into a module you `setattr` it onto — Python classes are named by where they were *defined*, Ruby classes by where they were *first assigned*. Row 6: a mixin is a class in the base tuple, and a namespace is a `types.ModuleType` object, so Ruby's one `Module` concept is two Python things. Row 7: `collections.namedtuple` and `dataclasses.make_dataclass` are the twins of `Struct.new` and `Data.define`. Row 8: `type(k)` is `type` — the class of a class is a class, and `isinstance(k, type)` is how you ask "is this a class?". Row 9: `__init_subclass__` always sees a name. Row 11 is the deepest divergence: `type("Meta", (type,), {})` is allowed, and it *is* a metaclass — Python lets you subclass the class of classes and customise class creation there, where Ruby refuses `Class.new(Class)` and uses singleton classes and hooks instead. Row 12: any string is a legal `__name__`. Row 13: a class in a module is an attribute, so `hasattr`/`delattr` on the module object replace `const_defined?`/`remove_const`. Row 14: a `class` statement inside a function also makes a fresh class per call, and its `__qualname__` records the nesting as `make_class.<locals>.Made`. Row 15: `types.new_class` and the four-argument `type(..., tag="y")` deliver keyword options to `__init_subclass__`, which Ruby's `Class.new` cannot do — a Ruby class takes its options by calling a class method after it exists.

```ruby
# classes_at_runtime_kata_rb.rb — temperature classes generated from a table.

class Temperature
  attr_reader :value
  def initialize(value) = @value = value
end

TO_KELVIN = {
  Celsius:    ->(v) { v + 273.15 },
  Fahrenheit: ->(v) { (v + 459.67) * 5 / 9 },
  Kelvin:     ->(v) { v },
}

TO_KELVIN.each do |name, convert|
  klass = Class.new(Temperature) do
    define_method(:to_kelvin) { convert.call(value).round(2) }   # closes over this unit's lambda
  end
  Object.const_set(name, klass)                                  # gives it its name
end

puts "1. Celsius.name / superclass         -> #{Celsius.name} / #{Celsius.superclass}"
puts "2. Celsius.new(100).to_kelvin        -> #{Celsius.new(100).to_kelvin}"
puts "3. Fahrenheit.new(212).to_kelvin     -> #{Fahrenheit.new(212).to_kelvin}"
puts "4. Kelvin.new(373.15).to_kelvin      -> #{Kelvin.new(373.15).to_kelvin}"
puts "5. Temperature.subclasses names      -> #{Temperature.subclasses.map(&:name).sort.inspect}"
puts "6. Object.const_get(\"Celsius\").new(0).to_kelvin -> #{Object.const_get("Celsius").new(0).to_kelvin}"
```
