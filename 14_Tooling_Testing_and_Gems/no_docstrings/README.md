# Ruby has no docstrings

**Level:** 101 · a Python programmer who reaches for `help(obj)` and `obj.__doc__` and finds nothing of the kind in Ruby

**One line:** A Ruby method carries no documentation at run time — only `source_location`, the file and line of its `def` — and the comment above the `def` is the documentation by convention, read from the file by RDoc, YARD and `ri`; Python's docstring is a real object (`__doc__`), and `inspect.getcomments` does Ruby's trick too.

In Python a string literal that opens a `def`, `class` or module body is stored as `__doc__`; `help()` shows it, and every tool from IDE hovers to `pydoc` reads it. Ruby has nothing at run time: a comment is dropped by the parser. What a method does know is `source_location` — `[file, line]` for a method written in Ruby, `nil` for one implemented in C such as `Integer#+` or `Kernel#puts`. Documentation is therefore a convention on the source text: the comment block directly above a `def` belongs to it, and the tools agree on that. RDoc (a bundled gem) turns those comments into HTML and into the `ri` database, so `ri Array#each` at a terminal shows the comment from Ruby's own source; YARD adds tags to the same comments — `@param name [Type] description`, `@return [Type]`, `@example` — and generates richer pages *(Not machine-checked here.)*. The program below is a ten-line reader that does what those tools do: take `source_location`, open the file, and walk up from the line above the `def` while the lines are comments.

## Reading the output

Row 1 shows `source_location` for `add`: the program's own file name and the line of its `def`, a String and an Integer. Row 2 shows the `nil` you get for a method written in C — no file to read, so no comment to find, which is exactly why `ri` ships its own database extracted from the C sources' comments. Rows 3–5 are the reader at work: two comment lines above `add`, one above `Calc#mul`, none above `undocumented`. Row 6 proves the negative: `Method` has no `doc`, `documentation` or similar method at all. Row 7 is the underlying fact stated plainly — after parsing, the text `# Adds two numbers.` exists nowhere in memory. Row 8 hands the same comment to RDoc's markup parser, which sees two paragraphs; this is the first step of what `rdoc` and `ri` do with every comment in a file.

## Compared with Python

Row 1 is the same information through `inspect.getsourcefile` and `getsourcelines`. Row 2 is the same C-function limit — `getsourcefile(len)` raises `TypeError` — with the difference that `len.__doc__` still exists, because a C function's docstring is compiled into the interpreter. Rows 3–5 are `inspect.getcomments`, which reads the comment block above an object from its source file exactly as the Ruby program did, and returns `None` when there is none. Rows 6–8 are what Ruby lacks: `sub.__doc__` is a real string, `Calc.__doc__` too, and `inspect.getdoc` returns it with the indentation removed — use `getdoc` rather than raw `__doc__` when you print one, because 3.13 started stripping that indentation at compile time and the raw string differs between 3.12 and 3.14 *(Not machine-checked here.)*. `help(sub)` at the prompt prints the signature and this cleaned docstring, and `python3 -m pydoc sub` does the same from the shell. PEP 257 fixes the layout — a one-line summary, a blank line, then detail — and that is the shape `getdoc(sub)` shows in row 8.

```ruby
# Kata: a `Documented` hook. Extending a class with it makes `method_added`
# look at the source line above each new `def` and report whether a comment
# is there.
module Documented
  def method_added(name)
    file, line = instance_method(name).source_location
    above = File.readlines(file, chomp: true)[line - 2].to_s.strip
    puts format("%-18s %s", "#{self}##{name}:", above.start_with?("#") ? "documented (#{above})" : "NO COMMENT ABOVE")
    super
  end
end

class Calc
  extend Documented

  # Adds two numbers.
  def add(a, b) = a + b

  def sub(a, b) = a - b

  # Multiplies, the long way.
  def mul(a, b) = a * b
end
```
